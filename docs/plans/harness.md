## 1. Goal

Rustybin today is the upstream: a gateway sends traffic to it. Harness mode lets Rustybin also be the
client, and lets several Rustybin instances form a cluster. Clients drive load through the gateway under
test and servers act as its upstreams. The two sides correlate every request, so a run shows what the
gateway did and not only what the client saw.

```
                 leader (the coordinator role, held by one node at a time; failover in section 9.1)
                     join / heartbeat / assignments |        ^ stats, histograms
                 +----------------------------------+--------+-----------------+
                 v                                  v                          v
          client nodes  ===== load =====>   gateway under test   =====>   server nodes
          (1..n Rustybin,                   (one node or a fleet)         (1..m Rustybin,
           each 1..k virtual                                               the upstream pool)
           clients, chaos)  <==== responses (tagged by the server, or made by the gateway)
```

What it is for:

1. **Gateway performance at scale**: a cluster-wide request rate split over many client nodes, against
   one gateway or a fleet. It reports the overhead the gateway adds (client latency minus upstream
   processing time) rather than only end-to-end latency.
2. **Attribution**: every response is classified as answered by an upstream, generated by the gateway
   (its 429, 401, 503), or a transport failure. Requests that reached nobody are counted as lost.
3. **Behaviour under stress and chaos**: rate limits per consumer, circuit breakers, retries, health
   checks, and upstream node churn, with clients and upstreams that misbehave on purpose.
4. **Automation first**: the same control API and MCP tools drive it from CI, an agent, the console or
   the platform (`rustybin-platform`). Headless mode needs no controller at all.

Why not just k6 or similar? Those see only the client side. The harness knows the upstream side too.
It is one binary that is already the upstream, it can loop through (one process on both sides of the
gateway), and it generates traffic from the same OpenAPI mocks the upstream serves.

## 2. Vocabulary

| Term | Meaning |
|---|---|
| **Node** | One Rustybin process in harness mode, with one or more roles |
| **Role** | `client` (generates load), `server` (an upstream that correlates and reports), `coordinator` (owns a cluster: membership, runs, merged results). A node may hold several roles; `both` is shorthand for `client,server` (loop-through) |
| **Cluster** | A named group of nodes (`cluster_id`) managed by one coordinator |
| **Leader** | The node currently holding the coordinator role. Exactly one per cluster and term; every node knows who it is (section 9.1) |
| **Term** | A counter that increases with every change of leader. Every message carries it, and a message from an older term is refused, so a leader that comes back after a failover cannot act |
| **Eligible node** | A node that may become leader: it advertises a control URL the other nodes can reach. Nodes that cannot be reached (behind NAT) still join and work, but never lead |
| **Succession list** | Eligible nodes ordered by least work, computed by the leader and replicated to every node, so all nodes agree on who takes over |
| **Scenario** | What to send, where, how fast, with which chaos and pass criteria (section 6) |
| **Run** | One execution of a scenario on a cluster: `run_id`, stages, live stats, final report |
| **Layer** | One stream of traffic inside a run, with its own source, identities and pattern (customers, an attacker, LLM calls); layers run at the same time and are reported separately (section 6) |
| **Pattern** | The shape of a layer's load over time: ramp, step, target, breakpoint, spike, pulse, burst, wave, burst attack (section 6.2) |
| **Scale** | How big a run is: client and server nodes, virtual clients, connections, identities (section 6.4) |
| **Virtual client (VU)** | One simulated client inside a client node: its own credentials, session, connection pool and source identity |
| **Headless mode** | Everything comes from env vars and a scenario file. Nodes self-assemble, the run starts on quorum, and the report goes to a file or stdout with an exit code. No controller is needed during the run |
| **Orchestrated mode** | Nodes start idle. A controller (platform, CI, agent over MCP, console) creates clusters and runs through the API. Same engine, same API |

## 3. Topologies

1. **Loop-through, one node** (`both`): the node's clients send through the gateway, and the gateway routes
   back to the same node's data plane. Both sides share one clock, so request-leg and response-leg
   latencies are exact. This is the smallest useful demo.
2. **Client and server pair**: one client node, one server node, the gateway between them.
3. **Cluster**: a coordinator, n client nodes (each with k virtual clients), and m server nodes as the
   gateway's upstream pool. The coordinator splits the cluster-wide rate across clients and merges results.
4. **External upstream**: clients only, in front of a real backend. Client-side metrics work. Attribution
   degrades to "server tag missing" (section 7), which is still useful to spot gateway-made responses by
   status and headers.
5. **Many gateways**: a scenario lists several targets with weights (gateway nodes, regions, or two
   gateways compared side by side under identical load).

## 4. How it fits the existing code

- **New module `src/harness/`** with `mod.rs` (router, catalogue, OpenAPI), `scenario.rs` (model,
  validation, JSON Schema, built-in scenarios embedded from `src/harness/scenarios/*.yaml`), `pattern.rs`
  (pattern math and preview), `ratelimit.rs` (attacks and the rate-limit analysis), `engine.rs`
  (scheduler, virtual clients, HTTP client), `chaos.rs`, `correlate.rs` (headers, signing, the server
  layer), `cluster.rs` (coordinator, membership, leases, clock sync, elections),
  `report.rs` (histograms, timelines, thresholds), `safety.rs` (allowlist, caps, target verification),
  `cli.rs` (`rustybin harness ...`). Registered like any module (`ROUTERS`, `SOURCES`, `MODULE_PATHS`).
- **State**: module-local behind `Extension`. Every map is bounded (section 10). No new `AppState`
  field unless the correlation layer needs it from `build_app`, which it does, so it gets one
  (`harness: Option<Arc<Harness>>`, `None` when harness mode is off).
- **Correlation layer** in `build_app`, next to inspector capture. It reads harness headers on data-plane
  requests, records per-run server stats and adds `Server-Timing` plus the signed served-by tag to the
  response. It is a no-op (one header lookup) when no harness header is present.
- **HTTP client**: `hyper` 1 with `hyper-util`'s client and `tokio-rustls`. `hyper-util` moves from
  dev-dependencies to dependencies. Raw connections are needed for chaos (slow bodies, resets, half-open
  connections, connection churn), which `reqwest` hides; `reqwest` stays for the existing uses.
  HTTP/1.1, HTTP/2 (ALPN and prior knowledge), TLS with SNI override, optional client certificate from
  the demo PKI for mTLS gateways.
- **Separate runtime**: the engine runs on its own multi-threaded tokio runtime
  (`RUSTYBIN_HARNESS_THREADS`, default half the cores in `both` mode, all of them on client-only
  nodes). Load generation therefore never starves the node's own data plane in loop-through.
- **Histograms**: `hdrhistogram` (mergeable, serialisable). Nodes ship compressed histogram deltas in
  heartbeats; the coordinator merges them exactly, with no averaging of percentiles.
- **Mocks**: requests can be generated from a deployed mock (`mocks::checks` already builds a valid
  request per operation; `schema.rs` generates bodies). The scenario names a mock, and the client asks
  its own instance or the coordinator for the spec.
- **Existing upstream behaviour**: server nodes already serve everything Rustybin serves (`/echo`,
  `/delay`, `/status`, mocks, `/ai`, `/mcp`, gRPC, WebSocket). Fault headers (`X-Rustybin-Delay`,
  `X-Rustybin-Fail`) already exist. A new shaped endpoint (section 8) adds per-run response profiles.
- **Control plane**: `/_rustybin/harness/*`, protected by `control_auth::enforce`, except the node
  routes, which verify a node credential themselves (section 9).

## 5. Modes and configuration

Off by default. Nothing in this plan sends a request unless `RUSTYBIN_HARNESS` is set.

| Env var | |
|---|---|
| `RUSTYBIN_HARNESS` | `off` (default) or `on` |
| `RUSTYBIN_HARNESS_ROLES` | `client`, `server`, `coordinator`, `both`, comma separated (default `server` when on) |
| `RUSTYBIN_HARNESS_TARGETS` | Required for the client role: allowed target hosts and CIDRs (`gw.example.com,10.0.0.0/8`). No default; nothing is allowed without it |
| `RUSTYBIN_HARNESS_VERIFY_TARGETS` | `on` requires target ownership proof before a run (section 11); default `on` in hosted mode |
| `RUSTYBIN_HARNESS_CLUSTER` | Cluster id to create (coordinator) or join (others) |
| `RUSTYBIN_HARNESS_JOIN` | Coordinator URL to join (`https://coord/_rustybin/harness/clusters/<id>`) |
| `RUSTYBIN_HARNESS_JOIN_TOKEN` | Shared join secret (a platform pod secret) |
| `RUSTYBIN_HARNESS_ADVERTISE` | Server nodes: their data-plane URL as the gateway reaches it (for upstream export) |
| `RUSTYBIN_HARNESS_CONTROL_URL` | This node's control URL as the other nodes reach it. Set means eligible to lead; unset means never leader |
| `RUSTYBIN_HARNESS_LEADER` | `auto` (default: eligible when the control URL is set), `prefer` (a standby: listed first in succession whatever its work), `never` |
| `RUSTYBIN_HARNESS_ELECTION_TIMEOUT` | How long without the leader before an election starts (default 3 s, always less than the lease) |
| `RUSTYBIN_HARNESS_SCENARIO` | Headless coordinator: scenario file to run |
| `RUSTYBIN_HARNESS_START` | `manual` (default), `on-quorum` (start once `min_nodes` per role joined) or `immediately` |
| `RUSTYBIN_HARNESS_REPORT` | Headless: write the final report here (`-` for stdout) |
| `RUSTYBIN_HARNESS_EXIT` | Headless: exit after the run, code 0 when thresholds pass, 1 when they fail, 2 on error |
| `RUSTYBIN_HARNESS_DATA_PLANE` | `off` on client-only nodes: serve only `/`, `/_rustybin/*` and `/ui`, which shrinks the surface |
| `RUSTYBIN_HARNESS_THREADS`, `..._MAX_RATE`, `..._MAX_INFLIGHT`, `..._MAX_DURATION` | Engine caps per node (section 10) |

Refused at startup, with a fatal error (not a warning): harness mode with `RUSTYBIN_PUBLIC_MODE`, with
self-service mocks, or the client role without `RUSTYBIN_HARNESS_TARGETS`. Invalid optional values warn
and default like other config.

### Headless

```bash
# coordinator: waits for 4 clients and 2 servers, runs the scenario, writes the report, exits 0 or 1
RUSTYBIN_HARNESS=on RUSTYBIN_HARNESS_ROLES=coordinator RUSTYBIN_HARNESS_CLUSTER=perf-1 \
RUSTYBIN_HARNESS_JOIN_TOKEN=... RUSTYBIN_HARNESS_SCENARIO=gateway-smash.yaml \
RUSTYBIN_HARNESS_START=on-quorum RUSTYBIN_HARNESS_REPORT=- RUSTYBIN_HARNESS_EXIT=on rustybin

# every other node: a role, the join URL and the token
RUSTYBIN_HARNESS=on RUSTYBIN_HARNESS_ROLES=client RUSTYBIN_HARNESS_TARGETS=gw.internal \
RUSTYBIN_HARNESS_JOIN=https://coord:8080/_rustybin/harness/clusters/perf-1 RUSTYBIN_HARNESS_JOIN_TOKEN=... rustybin
```

This fits a Kubernetes Job plus Deployments, a compose file, or n Fly machines. The CLI mirrors it for a
single process: `rustybin harness run scenario.yaml` (client, plus an optional local server on a port for
loop-through), `rustybin harness validate scenario.yaml`, `rustybin harness report report.json`
(a text summary, or JUnit for CI).

### Orchestrated

Nodes start with a role and no run. A controller drives everything through the API (section 9) or the
management MCP tools (section 13): create a cluster, have nodes join (env at boot, or
`POST /_rustybin/harness/join` on each node later), submit a scenario, start, watch, stop, fetch the
report.

## 6. Scenario: run patterns, scale and parameters

A scenario is the full set of parameters for a run: where to send, what to send, the shape of the load
over time, the scale, chaos, and pass criteria. There is one model (`scenario.rs`) and one JSON Schema
generated from it. The API, scenario files, the MCP tools and the console all read and write that same
model, so every parameter can be set and tuned from any of them (section 6.6).

```yaml
name: rate-limit-under-attack
targets:
  - url: https://gw.example.com          # must be in RUSTYBIN_HARNESS_TARGETS
    weight: 3
    host: api.example.com                # Host / SNI override
    http: h2                             # h1 | h2 | h2c
  - url: https://gw-eu.example.com
    weight: 1
scale:                                   # section 6.4
  client_nodes: 4                        # or auto
  virtual_clients: 2000
  connections_per_client: 2
layers:                                  # traffic layers run at the same time, reported separately
  - name: customers                      # legitimate traffic
    source: { mock: petstore, operations: { exclude: [deletePet] }, invalid_fraction: 0.02 }
    identities: { api_keys: { header: apikey, mint: 200 } }
    pattern: { type: ramp, from: 100, to: 3000, over: 2m, then: { type: constant, rate: 3000, for: 10m } }
  - name: attacker                       # one consumer far over its limit
    source: { request: { method: GET, path: /echo?n={{seq}} } }
    identities: { api_keys: { header: apikey, values: [victim-key] } }
    pattern: { type: burst_attack, attack: window_edge, window: 60s, burst: 500, every: 1 }
    starts_after: 3m
    expect: { limit: 100, window: 60s, per: key }   # section 6.3
  - name: llm
    source: { llm: { path: /ai/v1/chat/completions, stream: true, tokens: 200 } }
    pattern: { type: pulse, high: 50, low: 0, on: 20s, off: 40s }
connections: { reuse: true, churn: 0.0 }
chaos: { preset: flaky-upstream }        # section 8
servers:                                 # upstream profile for the shaped endpoint, pushed to server nodes
  latency: { p50: 20ms, p99: 250ms }
  status: { "200": 97, "503": 3 }
  body_bytes: 2048
thresholds:
  gateway_overhead_p99: 15ms
  error_rate: 0.01                       # transport errors plus unexpected statuses
  lost: 0
  upstream_reach: 0.98
  layers:
    customers: { rate_limited: 0.001 }   # collateral damage: legitimate traffic must not be throttled
    attacker: { over_admission: 0.02 }   # the limiter may let at most 2 percent too many through
```

Validation is offline and lists every problem (targets outside the allowlist, unknown mocks, rates over
the caps, durations over the maximum, layers whose peak rates add up to more than the scale allows).

**Traffic layers** are the main idea. A real gateway serves legitimate users while being hammered, so a
run has several layers, each with its own source, identities and pattern, running at the same time. Every
result is reported per layer as well as in total. A rate-limit test can therefore show both sides: the
attacker being throttled, and the customers not being throttled (collateral damage). A scenario with one
layer is the simple case and can be written without `layers:`.

### 6.1 Load models

- **Open** (the default): requests are scheduled at intended times. Latency is measured from the intended
  send time (corrected for coordinated omission) and also from the actual send time, and both are reported.
  When the in-flight cap is hit, requests are counted as `not_sent` and the client is flagged as
  saturated, rather than slowing down silently.
- **Closed**: a number of virtual users, each with think time. Patterns then shape the number of active
  users instead of the request rate (`unit: users`).

### 6.2 Run patterns

A pattern is a function of time that gives the target rate (or users) of a layer. Patterns run in
sequence with `then:`, and the leader evaluates them on the cluster clock so every node switches at the
same tick.

| Pattern | Parameters | What it tests |
|---|---|---|
| `constant` | `rate`, `for` | Baseline, soak (`for: 8h` with latency drift and memory checks in the report) |
| `ramp` (scale) | `from`, `to`, `over`, `curve: linear \| exponential` | Behaviour as load grows; where latency bends |
| `step` | `start`, `step`, `every`, `max`, `hold` | Capacity plateaus: each step is held and reported on its own |
| `target` | `rate` or `users` or `overhead_p99`, `within`, `hold` | Reach and hold a load target. `overhead_p99` is a closed loop: the leader adjusts the rate until the gateway overhead sits at the target |
| `breakpoint` | `start`, `growth`, `until` (thresholds), `max` | Find the maximum sustainable rate: grow until a threshold fails, then stop and report the last good rate |
| `spike` | `base`, `peak`, `rise`, `hold`, `fall`, `recover` | A sudden surge and how long the gateway takes to recover (time back to baseline latency and errors) |
| `pulse` | `high`, `low`, `on`, `off`, `cycles`, `jitter` | A square wave: autoscaling, connection pools and limiters that refill between pulses |
| `burst` | `base`, `size`, `within`, `every`, `jitter` | Short spikes: `size` requests sent within `within` (for example 1,000 in 50 ms) every `every`, on top of a base rate; queueing and burst allowances (token buckets) |
| `wave` | `min`, `max`, `period`, `shape: sine \| triangle \| sawtooth` | Smooth periodic load, a daily curve compressed in time |
| `burst_attack` | section 6.3 | Rate limiting and abuse protection |
| `replay` (later) | a recorded timeline | Real traffic shapes (open question 4) |

Every pattern accepts `jitter` (random variation per tick) and `sync: cluster | node`. With `cluster`
(the default), all client nodes follow the same curve in lockstep, so a burst arrives at the gateway as one
burst. With `node`, each node runs its own phase, which spreads the load.

### 6.3 Burst attacks: testing rate limiting

`burst_attack` patterns are built to break rate limiters, and the report checks the limiter against what
the scenario expects (`expect: {limit, window, per: key | ip | consumer | route | global}`).

| Attack | What it sends | What it finds |
|---|---|---|
| `flood` | One identity at a multiple of its limit (`factor: 10`) | Basic enforcement, time to the first 429, how many got through |
| `window_edge` | `burst` requests just before a window boundary and again just after, aligned to the wall clock | Fixed-window double dipping (up to twice the limit within one window length) |
| `just_under` | 90 to 100 percent of the limit, for a long time | False positives: legitimate users throttled under the limit |
| `distributed` | All client nodes burst the same identity at the same cluster tick, through several gateway nodes | Limiters whose counters are local to each gateway node, or slow to sync: over-admission per gateway node |
| `key_spray` | Many identities, each under its limit, adding up to far more than a global or per-IP limit | Whether global, per-IP and per-route limits hold when per-key limits are dodged |
| `ip_spray` | Rotating `X-Forwarded-For` (and real source addresses where the host has several) | Per-IP limits, and whether the gateway trusts forwarded headers it should not |
| `retry_storm` | Throttled clients retry at once, ignoring `Retry-After` (or honouring it, `honour_retry_after: true`) | Recovery under retries, and the difference that compliant clients make |
| `concurrency` | A burst of simultaneous new connections and in-flight requests rather than a rate | Connection and concurrency limits, accept queues |
| `slow_burn` | Rate rising slowly from under to over the limit | The exact rate where enforcement starts, compared with the configured limit |
| `limit_probe` | Binary search on the rate for one identity | The effective limit and window, measured, when the configuration is unknown |

The rate-limit analysis in the report (per layer and per identity, sampled up to a bounded number of
identities):

- requests admitted per window against the expected limit: over-admission and under-admission, per
  gateway node when the gateway exposes one (`Via`, or a configured response header);
- time to the first 429 and time to recovery after the attack stops;
- rate-limit headers: whether `RateLimit` / `RateLimit-Policy` (the IETF draft), `X-RateLimit-*` and
  `Retry-After` are present, consistent with what happened, and counting down correctly;
- collateral damage: throttling and latency in other layers during the attack;
- upstream protection: what reached the server nodes during the attack (from the correlation layer),
  which shows whether the limiter shields the upstream or only rewrites responses.

### 6.4 Scale

`scale` says how big the run is, separately from the patterns that say how hard it pushes.

| Parameter | |
|---|---|
| `client_nodes` | A number (wait for that many before starting) or `auto` |
| `server_nodes` | Expected upstream nodes; the run waits for them and checks the gateway reaches each (well-known path, section 11) |
| `virtual_clients` | Cluster-wide, split across client nodes by capacity |
| `connections_per_client` | Connection pool per virtual client, which sets the number of connections the gateway sees |
| `max_rate_per_node` | Lower than the node cap, to keep clients well below saturation |
| `identities` | How many distinct keys or tokens to mint or use, per layer |

With `client_nodes: auto`, the leader compares the scenario's peak rate with the measured capacity of the
nodes it has. When it needs more, it emits a `scale_request` event (`{needed_client_nodes, reason}`) on the
run feed. If the cluster has a controller hook configured, it also POSTs the event there. The hook URL is
allowlisted like targets, and the request is signed with the cluster secret. A controller such as the
platform answers by provisioning pods that join. The run starts when the scale is met, or after
`scale_timeout` with a warning that it runs undersized. Rustybin never starts machines itself.

### 6.5 Live tuning

A running run can be tuned without stopping it.

`PATCH .../runs/{run}` takes:

- `rate_multiplier` (0 to 10, for the whole run or one layer);
- `pause` and `resume` (all layers or one);
- `hold` (freeze the pattern at its current point);
- `skip_stage` (jump to the next `then:`);
- `set` (change any pattern parameter of a layer, for example `attacker.pattern.burst: 1000`);
- `add_layer` and `remove_layer`;
- `chaos` (change the preset or a behaviour).

The rules:

- Each change is validated against the same schema and caps as a new scenario.
- The leader applies it on the next cluster tick: heartbeats long-poll, so they return at once on a change.
- Each change is recorded in the run's timeline and audit log, so the report shows exactly when the
  approach changed and what it did.
- Changes are in the replicated snapshot, so they survive a failover.

### 6.6 One parameter model, three surfaces

The parameters are the source of control, and none of the surfaces can drift from the others:

- **Schema**: `GET /_rustybin/harness/schema` serves the JSON Schema of scenarios and live changes, with
  descriptions, units, defaults, minimums and maximums (the caps of this node).
- **API**: scenarios as JSON or YAML (`POST .../runs`), live changes (`PATCH .../runs/{run}`), a preview
  (`POST /_rustybin/harness/preview`: the expected rate per second per layer and the total, without
  sending anything), and saved scenarios (`GET/PUT/DELETE /_rustybin/harness/scenarios/{name}`, bounded,
  persisted with `RUSTYBIN_MOCKS_STATE_DIR`'s pattern).
- **MCP**: tool input schemas are built from the same JSON Schema (`create_run`, `update_run`,
  `preview_scenario`, `save_scenario`, `list_scenarios`, `list_patterns`).
- **UI**:
  - the scenario builder renders its form from the JSON Schema (vanilla JS, no build step, like the rest
    of `ui/`), with a YAML view of the same scenario;
  - a pattern preview chart from `preview`;
  - during a run, live controls: a rate multiplier slider, pause and hold per layer, skip stage, and edits
    to any pattern parameter.
- **Built-in scenarios**: YAML files under `src/harness/scenarios/`, embedded in the binary like `ui/`:
  `smoke`, `soak`, `ramp-to-target`, `breakpoint`, `spike-and-recover`, `pulse`, `burst`, and one per
  attack in section 6.3. They are listed next to saved scenarios and are a starting point to copy and tune.
- **Parity test**: a unit test walks the JSON Schema and fails when a parameter has no description or
  bounds, or is missing from the MCP tool schemas. A browser check (`conformance/ui/`) fails when the
  builder does not render a field for every schema property.

## 7. Correlation

Each harness request carries:

| Header | Value |
|---|---|
| `X-Request-Id` | `<run>-<node>-<seq>`, deterministic, so gateway access logs join with the report |
| `traceparent` | W3C, one trace per request, so a gateway with tracing shows the same id |
| `X-Rustybin-Harness` | `v1; run=<run_id>; node=<node_id>; seq=<n>; vu=<k>; sent=<unix_ns>; sig=<hmac>` |

The signature is an HMAC over the other fields with a run key the coordinator derives and hands only to
cluster members. Server nodes count only authentic harness traffic, so stray or spoofed headers on a
shared instance never pollute a run.

**Server side** (the correlation layer on every data-plane route of a server node):

- records per run: arrivals by node and operation, upstream processing time, and what the gateway
  changed on the request. The client sends a digest of the headers and body it sent; the server compares
  them and records sampled header adds, removes and rewrites, plus body integrity;
- answers with `Server-Timing: rb;dur=<ms>` and `X-Rustybin-Served-By: <node>; run=<run_id>; sig=<hmac>`;
- samples captures into the inspector (1 in N plus every anomaly) instead of capturing every request, so
  a 20,000 rps run never floods the ring buffer or its feed.

**Client side** classifies every response:

| Class | How it is known |
|---|---|
| `upstream` | A valid served-by tag for this run |
| `gateway` | A response without the tag (a rate limit, auth failure, gateway 5xx, cached answer), broken down by status |
| `transport` | Connect, TLS, timeout, reset, protocol error, each counted on its own |
| `lost` (coordinator, after the run) | Sent, seen by no server, and no response or a transport error at the client: the gateway swallowed it |

**Latency breakdown**:

- `total`: client view;
- `upstream`: the server's `Server-Timing`;
- `overhead` = total minus upstream (gateway plus network, with no clock sync needed);
- with clock sync (section 9), `request_leg` and `response_leg` one-way times, reported with the sync
  error bound.

In loop-through on one node the clock is shared and the legs are exact.

**Logs**: with `RUSTYBIN_LOG_FORMAT=json`, every node logs harness events with `run_id`, `node_id`, `seq`
and `trace_id`, so logs from clients, servers and the gateway join on the same ids.

## 8. Chaos

Client behaviours, each with a probability or rate, all bounded by the caps:

- connection churn (new connection per request, TLS handshake storms), keep-alive abuse;
- abandoned requests (cancel after n ms), half-open connections, resets mid-body;
- slow request bodies (a bounded trickle), oversized headers near common limits, malformed JSON, wrong
  content types;
- retry storms (immediate retries on 5xx), thundering herd (synchronised bursts across all nodes at the
  same coordinator tick), credential churn (expired and revoked tokens);
- protocol mix (HTTP/1.1 and HTTP/2 against the same route), WebSocket floods and SSE readers that never
  read (phase 7).

Server behaviours, applied by server nodes to authentic harness traffic only:

- the shaped endpoint `/harness/{*path}`: per-run latency distribution, status mix, body size, chunked
  or streamed responses, slow first byte;
- flapping health (`/health` toggled on a schedule), connection drops, stalls after headers;
- node churn: the coordinator tells a server node to stop accepting for n seconds or to leave and
  rejoin, which exercises the gateway's health checks and circuit breakers.

Presets: `calm`, `jittery`, `flaky-upstream`, `retry-storm`, `thundering-herd`, `churn`, `mad` (all of
them at once). A preset is just a named chaos block; scenarios can override any field.

## 9. Cluster protocol

In steady state, nodes pull. They call the leader and the leader never calls them, so nodes behind NAT,
in other regions or on a private network all work. Only elections need node-to-node calls, and only
between eligible nodes (section 9.1).

Controller routes are answered by the leader. On any other node they answer
`307 Temporary Redirect` to the same path on the leader. The redirect carries
`X-Rustybin-Harness-Leader: <node_id>; term=<n>` and a JSON body naming the leader. A controller can
therefore talk to any node it knows and follow the redirect. Clients that do not follow redirects read the
body.

| Route | Who calls it | |
|---|---|---|
| `GET /_rustybin/harness` | anyone with control access | Node status: roles, cluster, current run, caps, `harness_api: 1`, and `leader: {node_id, control_url, term, since}` as this node sees it |
| `GET /_rustybin/harness/clusters/{id}/leader` | controller, any node | The leader, the term, the succession list with each node's work score, and the history of leader changes. Answered by every member (never redirected), so a controller can always find the leader |
| `POST /_rustybin/harness/join`, `/leave` | controller | Tell this node to join or leave a coordinator (orchestrated) |
| `POST /_rustybin/harness/stop` | controller | Kill switch: stop all local load now |
| `POST /_rustybin/harness/clusters` | controller | Create a cluster: `{cluster_id?, min_nodes?}` returns the id and a join token |
| `GET /_rustybin/harness/clusters/{id}` | controller | Members, roles, health, clock offsets, current run |
| `GET /_rustybin/harness/clusters/{id}/upstreams` | controller | Server nodes' advertised URLs as a plain JSON list, for configuring the gateway's upstream pool |
| `POST /_rustybin/harness/clusters/{id}/runs` | controller | Submit a scenario; returns `run_id` (validated, not started) |
| `POST .../runs/{run}/start`, `/stop` | controller | Start (synchronised) or stop |
| `PATCH .../runs/{run}` | controller | Live tuning (section 6.5) |
| `GET /_rustybin/harness/schema` | controller, any node | JSON Schema of scenarios and live changes, with this node's caps as bounds (section 6.6) |
| `POST /_rustybin/harness/preview` | controller, any node | Expected rate per second per layer for a scenario, without sending anything |
| `GET`, `PUT`, `DELETE /_rustybin/harness/scenarios/{name}`, `GET /_rustybin/harness/scenarios` | controller | Saved scenarios plus the built-in ones (read only) |
| `GET .../runs/{run}` | controller | Live merged stats |
| `GET .../runs/{run}/events` | controller | SSE feed of 1 s snapshots (the console reads it with `send({stream: true})`) |
| `GET .../runs/{run}/report` | controller | Final report (JSON; `?format=junit` or `text`) |
| `POST /_rustybin/harness/clusters/{id}/nodes` | node, join token | Join: `{node_id, roles, advertise, capacity, version}` returns a node credential and a lease |
| `POST .../nodes/{node}/heartbeat` | node, node credential | Long poll (up to 10 s): carries stats deltas, histograms, clock-sync stamps, the node's work report and its term; returns an assignment, a profile, `stop`, and the latest cluster state snapshot when its version changed |
| `POST .../election/vote` | eligible node, node credential | A candidate asks for a vote: `{term, candidate, snapshot_version}`; answer `{granted, term, leader?}` |
| `POST .../election/elected` | new leader, node credential | Announces the new term to eligible peers so they stop waiting; the other nodes learn on their next heartbeat |

- **Single node** is a cluster of one with the node as its own coordinator. `POST /_rustybin/harness/runs`
  is shorthand for that, so the simplest use needs no cluster at all.
- **Assignments**: the coordinator gives each client its share of the rate (by declared capacity), its
  range of virtual clients and credentials, the scenario hash, and a `start_at` in the node's own clock.
  Server nodes get the server profile and the run key.
- **Clock sync**: NTP-style timestamps on every heartbeat. The coordinator keeps an offset and an error
  bound per node, used for synchronised starts, thundering-herd ticks and one-way legs.
- **Leases, the dead man's switch**: a client stops sending if it has had no heartbeat answer from a
  leader for a lease period (default 5 s, renewed by any leader of the current or a newer term). An
  election finishes inside the lease, so a failover does not stop the load. A cluster that cannot elect a
  leader in time (a partition, too few nodes left) stops sending, and can never leave a herd running.

### 9.1 Leadership and failover

The coordinator role moves between nodes. One node leads at a time, everyone can see which one, and when it
dies the node doing the least work takes over and changes role.

**Who leads first**: the node started with the `coordinator` role (headless), or the node a controller
created the cluster on (orchestrated). It starts term 1.

**Everyone knows the leader**: the leader's id, control URL and term are in:

- every heartbeat answer;
- `GET /_rustybin/harness` on every node;
- `GET .../leader` on every member;
- the `X-Rustybin-Harness-Leader` header on redirects;
- the run's SSE feed (a `leader_changed` event).

**Replicated cluster state**: each node needs enough state to continue the run if it becomes leader, so
the leader replicates a versioned snapshot:

- membership and roles;
- the run, its scenario and stage, and each node's assignment;
- the succession list;
- the last merged totals and histograms (a checkpoint every 5 s);
- the run key, and the cluster secret that node credentials and join-token hashes derive from.

Every node gets the snapshot without the secrets. Eligible nodes also get the secrets: only they can lead,
and only they need to verify credentials. The snapshot is bounded in size (section 10) and sent only when
its version changes.

**Least work**: each heartbeat carries the node's work report:

- its assigned share of the rate;
- requests in flight and virtual clients;
- upstream arrivals per second (server role);
- CPU and scheduler lag.

The leader turns that into a work score and orders eligible nodes by it, ascending: the succession list.
`prefer` nodes (standbys) come first, so an idle standby coordinator is always the natural successor.
Ties break by node id, so the order is total. Because the list is in the snapshot, every node agrees on
the order without talking to the others.

**Election** (a Raft-style vote, with the candidate order fixed by the succession list instead of
random timeouts):

1. A node that gets no heartbeat answer for the election timeout (3 s) considers the leader gone.
2. The first live node in its succession list becomes the candidate. A node at position k waits
   k x 500 ms before standing, so position 1 normally wins without a contest.
3. The candidate raises the term and asks the eligible nodes for votes. A node grants its vote when it
   has also lost the leader, has not voted in this term, and the candidate's snapshot is at least as
   recent as its own. A node that still hears the old leader refuses. That prevents a false failover
   when only the candidate's own link is down.
4. With votes from a majority of the eligible nodes in the last snapshot, the candidate becomes leader
   and announces the new term. A candidate that fails gives way to the next position after its wait.
5. Non-eligible nodes keep heartbeating against the last leader and then fall back to the URLs in their
   snapshot's succession list until one answers with a newer term. They learn the new leader without
   voting.

**Changing role**: the new leader adds the `coordinator` role.

- By default (`leader_sheds_load: true` in the scenario) it hands its client share back. The rate is
  re-split over the remaining clients on their next heartbeat, so the cluster-wide rate stays as the
  scenario says.
- It keeps its server role. The gateway's upstream pool must not change because of an election.
- It resumes the run from the last checkpoint: it keeps the stage clock, and nodes report cumulative
  counters and histograms since the run started (not deltas since the last ack), so their first
  heartbeat to the new leader fills the gap exactly.
- The only data that can be lost is the dead leader's own client traffic since its last checkpoint. The
  report shows it as `unreported` with an upper bound, never silently.

**The old leader comes back**: every message carries the term. A node that sees a newer term steps down
at once: it drops the coordinator role, stops answering controller routes (redirecting instead) and
rejoins as an ordinary member. Its own requests are refused as stale until it does. No two leaders can act
in the same term.

**Two-node and one-node clusters**: a majority of two is two, so a two-node cluster cannot fail over. It
behaves like v1 without failover: the leases expire and the run stops. The plan says so in the docs, and
`GET .../leader` reports `failover: unavailable` until at least three eligible nodes have joined.

**Controller handover**: a controller watching the SSE feed gets `leader_changed`, then the stream
ends; it reconnects to the new leader's URL from the event. A controller holding only one node's URL
follows the redirect. The platform stores the cluster's eligible URLs and asks any of them.

## 11. Safety

Load generation is the first time Rustybin sends load to targets a caller chooses, so the fences come
first and are tested first. (A2A push notifications already send single requests to caller-supplied URLs,
behind `RUSTYBIN_A2A_PUSH_ALLOWLIST`; the leads webhook and the key registry URL are operator-set. The
harness allowlist and verification follow the same idea at load scale.)

- Off by default; fatal with public mode or self-service (section 5). The hosted demo never enables it.
- **Target allowlist** on every client node (`RUSTYBIN_HARNESS_TARGETS`). Names are resolved, and the
  resolved addresses are checked and pinned for the run (no DNS rebinding). Link-local, metadata
  (`169.254.169.254`, `fd00:ec2::254`) and the node's own control plane are always refused. A node checks
  every assignment against its own allowlist, so even a compromised coordinator cannot aim it elsewhere.
- **Target verification** (`RUSTYBIN_HARNESS_VERIFY_TARGETS`, on by default in hosted mode): before a
  run, each target must serve the run's verification token at `/.well-known/rustybin-harness`, or
  publish it as a DNS TXT record at `_rustybin-harness.<host>`. Server nodes in the cluster answer that
  path themselves. A gateway that routes to them therefore passes automatically, which also proves the
  route reaches the cluster before a single load request is sent. This is what lets a platform offer
  harness runs without becoming a way to flood third parties.
- **Authorisation**: a new control scope `harness`. The admin token and the `admin` scope imply it.
  The management MCP gets `Right::Harness`. Node routes accept only join tokens and node credentials,
  never control tokens. Join tokens and node credentials are compared in constant time and never logged.
- **Failover does not widen anything**: a new leader can only hand out assignments that every node still
  checks against its own allowlist, and an election never starts a run that was not running. Secrets go
  only to eligible nodes, over the authenticated node routes. Votes and announcements carry the node
  credential and the term. A node outside the last snapshot's membership can neither vote nor stand.
- **The kill switch reaches every leader**: `POST /_rustybin/harness/stop` on any node stops its own load
  and is forwarded to the leader. A stopped run stays stopped across a failover, because the stop is in
  the replicated snapshot.
- **Caps** (sections 9 and 10). Audit lines for cluster create, join, leave, run
  start and stop, kill, elections and leader changes, without scenario bodies or credentials.
- **Controller hook** (`scale_request`, section 6.4): off unless configured; its URL must be in the
  allowlist, the request is signed with the cluster secret, and it carries no scenario or credentials.
- **Live changes go through the same fences**: a `PATCH` is validated against the schema, the caps and
  every node's allowlist like a new scenario. A rate multiplier cannot lift a run above the caps.
- Credentials in scenarios (API keys, client secrets) are redacted in every read, report and log, like
  key redaction in captures.

## 12. Reports and metrics

The final report (JSON, plus `text` and `junit` renderings):

- run, scenario hash, nodes and roles, clock-sync quality, client saturation flags;
- leader changes: term, old and new leader, when, how long the cluster ran without a leader, the rate
  re-split, and any `unreported` traffic from the old leader. These events are also marked on the
  timeline, which shows what a failover did to the load;
- totals by class (`upstream`, `gateway` by status, `transport` by kind, `lost`, `not_sent`);
- latency percentiles (p50, p90, p99, p99.9, max) for `total`, `upstream`, `overhead`, and the legs when
  synced, overall and per target, operation, credential (consumer), client node and server node;
- every result per layer as well as in total;
- the timeline per stage and layer (rate achieved versus requested, latencies, classes), with pattern
  changes, live changes and leader changes marked on it, which shows where a rate limit or breaker
  kicked in and what each change did;
- the pattern results: the last good rate of a `breakpoint`, the time to recover from a `spike`, each
  `step`'s plateau, how far a `target` held from its goal;
- the rate-limit analysis of section 6.3 for layers with `expect`;
- what the gateway changed (sampled header adds, removes and rewrites, body integrity failures);
- thresholds with pass or fail and the measured value;
- samples with their `X-Request-Id` and `traceparent`, ready to look up in gateway logs.

Prometheus on every node: `rustybin_harness_requests_total{run,class,status}`,
`rustybin_harness_latency_seconds{run,kind}` (histogram), `rustybin_harness_inflight`,
`rustybin_harness_scheduler_lag_seconds`, `rustybin_harness_server_arrivals_total{run}`,
`rustybin_harness_term`, `rustybin_harness_is_leader`, `rustybin_harness_elections_total{outcome}`, with the run
label bounded (section 10). Reports can be kept on disk with `RUSTYBIN_HARNESS_REPORT_DIR`.

## 13. Surfaces

Every parameter is set the same way from the API, MCP and UI, from one schema (section 6.6).

- **Control API**: section 9, in the catalogue and OpenAPI like every route, with examples that run
  against a single-node loop-through.
- **Management MCP** (`src/mcp/manage/`):
  - tools: `harness_status`, `create_cluster`, `list_cluster_nodes`, `get_leader`, `export_upstreams`,
    `validate_scenario`, `preview_scenario`, `list_patterns`, `list_scenarios`, `save_scenario`,
    `create_run`, `start_run`, `update_run` (live tuning), `stop_run`, `get_run`, `get_run_report`;
  - input schemas come from the scenario JSON Schema, so a parameter added to the model is in the tools
    without further work;
  - every tool works on any node: the in-process call follows the leader redirect, and results name the
    leader that answered;
  - `start_run` sends real traffic to the outside world, so it gets `openWorldHint` and confirmation
    (elicitation, else `confirm: true`), like the destructive tools. So does `update_run` when it raises
    the rate or adds a layer;
  - `stop_run` needs no confirmation;
  - each tool has its `Right` and is filtered by role in `tools/list`;
  - prompts: `load_test_gateway` walks an agent through allowlist, scenario, preview, a dry run at a low
    rate, then the real run; `test_rate_limits` asks for the configured limits and builds the matching
    burst attacks with `expect` set.
- **Console**: a Harness page, shown only when harness mode is on:
  - cluster members (role, health, clock offset, work score, succession position) and a leader badge
    with the term and its history;
  - the scenario builder generated from the schema: targets, scale, layers and their patterns, with a
    preview chart that redraws as parameters change, a YAML view, built-in and saved scenarios;
  - the run view: live charts per layer (rate requested and achieved, latency percentiles, classes,
    429s), and the live controls of section 6.5;
  - the report, with the rate-limit analysis and samples.
- **CLI**: `rustybin harness run | validate | report | coordinator` (section 5).

## 14. Platform integration (decoupled)

The platform needs nothing harness-specific from core beyond this API. A harness on the platform is just
Rustybin pods with harness env plus calls to one coordinator:

1. Provision: n client pods (`p1` for heavy runs), m server pods, and one coordinator pod. For failover,
   two small standby pods with `RUSTYBIN_HARNESS_LEADER=prefer` give a successor that does no other work.
   Each pod gets `RUSTYBIN_HARNESS_*` env (with `RUSTYBIN_HARNESS_CONTROL_URL` = its pod URL, so it is
   eligible), and the join token as a pod secret, the same allowlisted `pod.secrets` path as
   `RUSTYBIN_ADMIN_TOKEN`.
2. Configure the customer's gateway upstream pool from `GET .../upstreams` (customer action, or their
   automation).
3. Drive runs with a platform-issued control JWT carrying the `harness` scope. The platform keeps the
   eligible pod URLs and calls any of them; redirects and `GET .../leader` take it to the current leader,
   so it never has to track failovers itself.
   With `client_nodes: auto`, the platform registers itself as the controller hook and answers
   `scale_request` events by provisioning more client pods, which join on their own.
4. Collect the report into insights; meter run hours with the existing load-test hours meter, or a new one.
5. Tear down: delete the pods. Leases make sure nothing keeps sending if teardown is late.

Platform rules (outside this repo): `RUSTYBIN_HARNESS_VERIFY_TARGETS` always on, targets limited to
verified customer domains, rate caps per plan, and a run cap per org. The platform side gets its own plan
in `rustybin-platform` (job kinds such as `harness_provision` and `harness_teardown`, the contract
additions, UI).

## 16. Testing

- Unit tests next to each part: scenario validation, scheduler timing (on the injectable clock that
  `limits::Clock` already provides), signing, classification, histogram merge, allowlist and pinning,
  lease expiry, succession ordering and tie breaks, vote rules, term fencing.
- Election tests run the nodes in one process on the injectable clock. A test can then drop links between
  chosen pairs (partitions, a candidate that only lost its own link) and advance time deterministically,
  with no sleeps.
- A test proxy in `src/harness/test_proxy.rs` (`cfg(test)`, a few dozen lines of hyper). It stands in for
  "the gateway": it adds and removes headers, answers its own 429 and 503, delays, and drops requests on
  command. It runs several instances to stand in for a gateway fleet. It has small reference rate
  limiters (fixed window, sliding window, token bucket; shared or per instance counters) with known
  flaws to switch on, so every burst attack has something to find. It is vendor neutral and fast.
- Pattern tests check the preview curve against the math and the achieved rate against the preview, on
  the injectable clock.
- Full-app tests start real servers on ephemeral ports (the `tests/integration.rs` pattern). Rates in
  tests stay low (hundreds of rps for a second or two) to keep the suite fast; throughput numbers belong
  to phase 0 and the conformance run, not to `cargo test`.

2. **OpenTelemetry export** (OTLP traces and metrics) from clients and servers, in addition to
   Prometheus and the report.
3. **HTTP/3** targets.
4. **Recording and replay**: replay captured inspector traffic (or a HAR file) as a traffic source.
5. **Scenario import** from other tools' formats, if users ask for it.
6. **Server-to-server chains**: servers that call further servers, for multi-hop meshes. That is
   outbound traffic from the server role, so it stays out until the safety model covers it.
