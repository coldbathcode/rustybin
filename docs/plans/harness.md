## 1. Goal

Rustybin today is the upstream: a gateway sends traffic to it. Load test mode lets Rustybin also be the
client, and lets several Rustybin instances form a cluster. Clients drive load through the gateway under
test and servers act as its upstreams. The two sides correlate every request, so a run shows what the
gateway did and not only what the client saw.

```
                 leader (the coordinator role, held by one node at a time; failover in section 9.1)
                     join / heartbeat / assignments |        ^ stats, histograms
                 +----------------------------------+--------+-----------------+
                 v                                  v                          v
          client nodes  ===== load =====>   gateway under test   =====>   server nodes
          (1..n Rustybin,                   (one node or a fleet)         (1..m Rustybin,
           each 1..k virtual                                               the upstream pool)
           clients, faults)  <==== responses (tagged by the server, or made by the gateway)
```

What it is for:

1. **Gateway performance at scale**: a cluster-wide request rate split over many client nodes, against
   one gateway or a fleet. It reports the overhead the gateway adds (client latency minus upstream
   processing time) rather than only end-to-end latency.
2. **Attribution**: every response is classified as answered by an upstream, generated by the gateway
   (its 429, 401, 503), or a transport failure. Requests that reached nobody are counted as lost.
3. **Behaviour under stress and faults**: rate limits per consumer, circuit breakers, retries, health
   checks, and upstream node churn, with clients and upstreams that fail on purpose.
4. **Automation first**: the same control API and MCP tools drive it from CI, an agent, the console or
   the platform (`rustybin-platform`). Headless mode needs no controller at all.

Why not just k6 or similar? Those see only the client side. The harness knows the upstream side too.
It is one binary that is already the upstream, it can loop through (one process on both sides of the
gateway), and it generates traffic from the same OpenAPI mocks the upstream serves.

## 2. Vocabulary

| Term | Meaning |
|---|---|
| **Node** | One Rustybin process in load test mode, with one or more roles |
| **Role** | `client` (generates load), `server` (an upstream that correlates and reports), `coordinator` (owns a cluster: membership, runs, merged results). A node may hold several roles; `both` is shorthand for `client,server` (loop-through) |
| **Cluster** | A named group of nodes (`cluster_id`) managed by one coordinator |
| **Leader** | The node currently holding the coordinator role. Exactly one per cluster and term; every node knows who it is (section 9.1) |
| **Term** | A counter that increases with every change of leader. Every message carries it, and a message from an older term is refused, so a leader that comes back after a failover cannot act |
| **Eligible node** | A node that may become leader: it advertises a control URL the other nodes can reach. Nodes that cannot be reached (behind NAT) still join and work, but never lead |
| **Succession list** | Eligible nodes ordered by least work, computed by the leader and replicated to every node, so all nodes agree on who takes over |
| **Scenario** | What to send, where, how fast, with which faults and pass criteria (section 6) |
| **Run** | One execution of a scenario on a cluster: `run_id`, stages, live stats, final report |
| **Layer** | One stream of traffic inside a run, with its own source, identities and pattern (customers, a heavy consumer, LLM calls); layers run at the same time and are reported separately (section 6) |
| **Pattern** | The shape of a layer's load over time: ramp, step, target, breakpoint, spike, pulse, burst, wave, rate-limit test (section 6.2) |
| **Scale** | How big a run is: client and server nodes, virtual clients, connections, identities (section 6.4) |
| **Virtual client (VU)** | One simulated client inside a client node: its own credentials, session, connection pool and source identity |
| **Headless mode** | Everything comes from env vars and a scenario file. Nodes self-assemble, the run starts on quorum, and the report goes to a file or stdout with an exit code. No controller is needed during the run |
| **Orchestrated mode** | Nodes start idle. A controller (platform, CI, agent over MCP, console) creates clusters and runs through the API. Same engine, same API |

## 3. Topologies

1. **Loop-through, one node** (`both`): the node's clients send through the gateway, and the gateway routes
   back to the same node's data plane. Both sides share one clock, so request-leg and response-leg
   latencies are exact. This is the smallest useful demo.
2. **Client and server pair**: one client node, one server node, the gateway between them.
3. **Cluster**: a coordinator, n client nodes (each with k virtual clients), and m server nodes as the
   gateway's upstream pool. The coordinator splits the cluster-wide rate across clients and merges results.
4. **External upstream**: clients only, in front of a real backend. Client-side metrics work. Attribution
   degrades to "server tag missing" (section 7), which is still useful to spot gateway-made responses by
   status and headers.
5. **Many gateways**: a scenario lists several targets with weights (gateway nodes, regions, or two
   gateways compared side by side under identical load).

## 4. How it fits the existing code

- **New module `src/harness/`** with `mod.rs` (router, catalogue, OpenAPI), `scenario.rs` (model,
  validation, JSON Schema, built-in scenarios embedded from `src/harness/scenarios/*.yaml`), `pattern.rs`
  (pattern math and preview), `ratelimit.rs` (rate-limit tests and their analysis), `engine.rs`
  (scheduler, virtual clients, HTTP client), `faults.rs`, `correlate.rs` (headers, signing, the server
  layer), `cluster.rs` (coordinator, membership, leases, clock sync, elections),
  `report.rs` (histograms, timelines, thresholds), `safety.rs` (allowlist, caps, target verification),
  `cli.rs` (`rustybin harness ...`). Registered like any module (`ROUTERS`, `SOURCES`, `MODULE_PATHS`).
- **State**: module-local behind `Extension`. Every map is bounded (section 10). No new `AppState`
  field unless the correlation layer needs it from `build_app`, which it does, so it gets one
  (`harness: Option<Arc<Harness>>`, `None` when load test mode is off).
- **Correlation layer** in `build_app`, next to inspector capture. It reads harness headers on data-plane
  requests, records per-run server stats and adds `Server-Timing` plus the signed served-by tag to the
  response. It is a no-op (one header lookup) when no harness header is present.
- **HTTP client**: `hyper` 1 with `hyper-util`'s client and `tokio-rustls`. `hyper-util` moves from
  dev-dependencies to dependencies. Raw connections are needed for faults (slow bodies, resets, half-open
  connections, connection churn), which `reqwest` hides; `reqwest` stays for the existing uses.
  HTTP/1.1, HTTP/2 (ALPN and prior knowledge), TLS with SNI override, optional client certificate from
  the demo PKI for mTLS gateways.
- **Separate runtime**: the engine runs on its own multi-threaded tokio runtime
  (`RUSTYBIN_HARNESS_THREADS`, default half the cores in `both` mode, all of them but one on client-only
  nodes). Load generation therefore never starves the node's own data plane in loop-through.
- **Scheduler thread** (phase 0): send times are kept by one dedicated OS thread, outside every runtime,
  which sleeps with `std::thread::sleep` and spawns each request onto the engine runtime. Scheduling on
  the engine runtime queued it behind the request tasks (10 ms of dispatch lag at 5,000 rps), and
  tokio's timer ticks in milliseconds. Worker threads leave the scheduler a core: when the process had
  more busy threads than cores, single lag spikes of 10 to 25 ms appeared even at 1,000 rps.
- **Histograms**: `hdrhistogram` (mergeable, serialisable). Each worker thread records into its own
  histograms, merged per one-second bucket (the spike's single locked histogram is not how the engine
  should do it). Nodes ship compressed histogram deltas in heartbeats; the coordinator merges them
  exactly, with no averaging of percentiles.
- **Mocks**: requests can be generated from a deployed mock (`mocks::checks` already builds a valid
  request per operation; `schema.rs` generates bodies). The scenario names a mock, and the client asks
  its own instance or the coordinator for the spec.
- **Existing upstream behaviour**: server nodes already serve everything Rustybin serves (`/echo`,
  `/delay`, `/status`, mocks, `/ai`, `/mcp`, gRPC, WebSocket). Fault headers (`X-Rustybin-Delay`,
  `X-Rustybin-Fail`) already exist. A new shaped endpoint (section 8) adds per-run response profiles.
- **Control plane**: `/_rustybin/harness/*`, protected by `control_auth::enforce`, except the node
  routes, which verify a node credential themselves (section 9).

## 5. Modes and configuration

Off by default. Nothing in this plan sends a request unless `RUSTYBIN_HARNESS` is set.

| Env var | |
|---|---|
| `RUSTYBIN_HARNESS` | `off` (default) or `on` |
| `RUSTYBIN_HARNESS_ROLES` | `client`, `server`, `coordinator`, `both`, comma separated (default `server` when on) |
| `RUSTYBIN_HARNESS_TARGETS` | Required for the client role: allowed target hosts and CIDRs (`gw.example.com,10.0.0.0/8`). No default; nothing is allowed without it |
| `RUSTYBIN_HARNESS_VERIFY_TARGETS` | `on` requires target ownership proof before a run (section 11); default `on` in hosted mode |
| `RUSTYBIN_HARNESS_CLUSTER` | Cluster id to create (coordinator) or join (others) |
| `RUSTYBIN_HARNESS_JOIN` | Coordinator URL to join (`https://coord/_rustybin/harness/clusters/<id>`) |
| `RUSTYBIN_HARNESS_JOIN_TOKEN` | Shared join secret (a platform pod secret) |
| `RUSTYBIN_HARNESS_ADVERTISE` | Server nodes: their data-plane URL as the gateway reaches it (for upstream export) |
| `RUSTYBIN_HARNESS_CONTROL_URL` | This node's control URL as the other nodes reach it. Set means eligible to lead; unset means never leader |
| `RUSTYBIN_HARNESS_LEADER` | `auto` (default: eligible when the control URL is set), `prefer` (a standby: listed first in succession whatever its work), `never` |
| `RUSTYBIN_HARNESS_ELECTION_TIMEOUT` | How long without the leader before an election starts (default 3 s, always less than the lease) |
| `RUSTYBIN_HARNESS_SCENARIO` | Headless coordinator: scenario file to run |
| `RUSTYBIN_HARNESS_START` | `manual` (default), `on-quorum` (start once `min_nodes` per role joined) or `immediately` |
| `RUSTYBIN_HARNESS_REPORT` | Headless: write the final report here (`-` for stdout) |
| `RUSTYBIN_HARNESS_EXIT` | Headless: exit after the run, code 0 when thresholds pass, 1 when they fail, 2 on error |
| `RUSTYBIN_HARNESS_DATA_PLANE` | `off` on client-only nodes: serve only `/`, `/_rustybin/*` and `/ui`, which shrinks the surface |
| `RUSTYBIN_HARNESS_THREADS`, `..._MAX_RATE`, `..._MAX_INFLIGHT`, `..._MAX_DURATION` | Engine caps per node (section 10) |

Refused at startup, with a fatal error (not a warning): load test mode with `RUSTYBIN_PUBLIC_MODE`, with
self-service mocks, or the client role without `RUSTYBIN_HARNESS_TARGETS`. Invalid optional values warn
and default like other config.

### Headless

```bash
# coordinator: waits for 4 clients and 2 servers, runs the scenario, writes the report, exits 0 or 1
RUSTYBIN_HARNESS=on RUSTYBIN_HARNESS_ROLES=coordinator RUSTYBIN_HARNESS_CLUSTER=perf-1 \
RUSTYBIN_HARNESS_JOIN_TOKEN=... RUSTYBIN_HARNESS_SCENARIO=gateway-load.yaml \

RUSTYBIN_HARNESS=on RUSTYBIN_HARNESS_ROLES=client RUSTYBIN_HARNESS_TARGETS=gw.internal \
RUSTYBIN_HARNESS_JOIN=https://coord:8080/_rustybin/harness/clusters/perf-1 RUSTYBIN_HARNESS_JOIN_TOKEN=... rustybin
```

This fits a Kubernetes Job plus Deployments, a compose file, or n Fly machines. The CLI mirrors it for a
single process: `rustybin harness run scenario.yaml` (client, plus an optional local server on a port for
loop-through), `rustybin harness validate scenario.yaml`, `rustybin harness report report.json`
(a text summary, or JUnit for CI).

### Orchestrated

Nodes start with a role and no run. A controller drives everything through the API (section 9) or the
management MCP tools (section 13): create a cluster, have nodes join (env at boot, or
`POST /_rustybin/harness/join` on each node later), submit a scenario, start, watch, stop, fetch the
report.

## 6. Scenario: run patterns, scale and parameters

A scenario is the full set of parameters for a run: where to send, what to send, the shape of the load
over time, the scale, faults, and pass criteria. There is one model (`scenario.rs`) and one JSON Schema
generated from it. The API, scenario files, the MCP tools and the console all read and write that same
model, so every parameter can be set and tuned from any of them (section 6.6).

```yaml
name: rate-limit-under-load
targets:
  - url: https://gw.example.com          # must be in RUSTYBIN_HARNESS_TARGETS
    weight: 3
    host: api.example.com                # Host / SNI override
    http: h2                             # h1 | h2 | h2c
  - url: https://gw-eu.example.com
    weight: 1
scale:                                   # section 6.4
  client_nodes: 4                        # or auto
  virtual_clients: 2000
  connections_per_client: 2
layers:                                  # traffic layers run at the same time, reported separately
  - name: customers                      # legitimate traffic
    source: { mock: petstore, operations: { exclude: [deletePet] }, invalid_fraction: 0.02 }
    identities: { api_keys: { header: apikey, mint: 200 } }
    pattern: { type: ramp, from: 100, to: 3000, over: 2m, then: { type: constant, rate: 3000, for: 10m } }
  - name: heavy_user                      # one consumer far over its limit
    source: { request: { method: GET, path: /echo?n={{seq}} } }
    identities: { api_keys: { header: apikey, values: [test-key] } }
    pattern: { type: limit_test, test: window_edge, window: 60s, burst: 500, every: 1 }
    starts_after: 3m
    expect: { limit: 100, window: 60s, per: key }   # section 6.3
  - name: llm
    source: { llm: { path: /ai/v1/chat/completions, stream: true, tokens: 200 } }
    pattern: { type: pulse, high: 50, low: 0, on: 20s, off: 40s }
connections: { reuse: true, churn: 0.0 }
faults: { preset: flaky-upstream }        # section 8
servers:                                 # upstream profile for the shaped endpoint, pushed to server nodes
  latency: { p50: 20ms, p99: 250ms }
  status: { "200": 97, "503": 3 }
  body_bytes: 2048
thresholds:
  gateway_overhead_p99: 15ms
  error_rate: 0.01                       # transport errors plus unexpected statuses
  lost: 0
  upstream_reach: 0.98
  layers:
    customers: { rate_limited: 0.001 }   # collateral damage: legitimate traffic must not be throttled
    heavy_user: { over_admission: 0.02 }   # the limiter may let at most 2 percent too many through
```

Validation is offline and lists every problem (targets outside the allowlist, unknown mocks, rates over
the caps, durations over the maximum, layers whose peak rates add up to more than the scale allows).

**Traffic layers** are the main idea. A real gateway serves legitimate users while it is under heavy load, so a
run has several layers, each with its own source, identities and pattern, running at the same time. Every
result is reported per layer as well as in total. A rate-limit test can therefore show both sides: the
heavy consumer being throttled, and the customers not being throttled (collateral damage). A scenario with one
layer is the simple case and can be written without `layers:`.

### 6.1 Load models

- **Open** (the default): requests are scheduled at intended times. Latency is measured from the intended
  send time (corrected for coordinated omission) and also from the actual send time, and both are reported.
  When the in-flight cap is hit, requests are counted as `not_sent` and the client is flagged as
  saturated, rather than slowing down silently.
- **Closed**: a number of virtual users, each with think time. Patterns then shape the number of active
  users instead of the request rate (`unit: users`).

### 6.2 Run patterns

A pattern is a function of time that gives the target rate (or users) of a layer. Patterns run in
sequence with `then:`, and the leader evaluates them on the cluster clock so every node switches at the
same tick.

| Pattern | Parameters | What it tests |
|---|---|---|
| `constant` | `rate`, `for` | Baseline, soak (`for: 8h` with latency drift and memory checks in the report) |
| `ramp` (scale) | `from`, `to`, `over`, `curve: linear \| exponential` | Behaviour as load grows; where latency bends |
| `step` | `start`, `step`, `every`, `max`, `hold` | Capacity plateaus: each step is held and reported on its own |
| `target` | `rate` or `users` or `overhead_p99`, `within`, `hold` | Reach and hold a load target. `overhead_p99` is a closed loop: the leader adjusts the rate until the gateway overhead sits at the target |
| `breakpoint` | `start`, `growth`, `until` (thresholds), `max` | Find the maximum sustainable rate: grow until a threshold fails, then stop and report the last good rate |
| `spike` | `base`, `peak`, `rise`, `hold`, `fall`, `recover` | A sudden surge and how long the gateway takes to recover (time back to baseline latency and errors) |
| `pulse` | `high`, `low`, `on`, `off`, `cycles`, `jitter` | A square wave: autoscaling, connection pools and limiters that refill between pulses |
| `burst` | `base`, `size`, `within`, `every`, `jitter` | Short spikes: `size` requests sent within `within` (for example 1,000 in 50 ms) every `every`, on top of a base rate; queueing and burst allowances (token buckets) |
| `wave` | `min`, `max`, `period`, `shape: sine \| triangle \| sawtooth` | Smooth periodic load, a daily curve compressed in time |
| `limit_test` | section 6.3 | Rate limiting and overuse protection |
| `replay` (later) | a recorded timeline | Real traffic shapes (open question 4) |

Every pattern accepts `jitter` (random variation per tick) and `sync: cluster | node`. With `cluster`
(the default), all client nodes follow the same curve in lockstep, so a burst arrives at the gateway as one
burst. With `node`, each node runs its own phase, which spreads the load.

### 6.3 Rate-limit tests

`limit_test` patterns probe rate limiters for their known weak spots, and the report checks the limiter against what
the scenario expects (`expect: {limit, window, per: key | ip | consumer | route | global}`).

| Test | What it sends | What it finds |
|---|---|---|
| `over_limit` | One identity at a multiple of its limit (`factor: 10`) | Basic enforcement, time to the first 429, how many got through |
| `window_edge` | `burst` requests just before a window boundary and again just after, aligned to the wall clock | Fixed-window double dipping (up to twice the limit within one window length) |
| `just_under` | 90 to 100 percent of the limit, for a long time | False positives: legitimate users throttled under the limit |
| `distributed` | All client nodes burst the same identity at the same cluster tick, through several gateway nodes | Limiters whose counters are local to each gateway node, or slow to sync: over-admission per gateway node |
| `many_keys` | Many identities, each under its limit, adding up to far more than a global or per-IP limit | Whether global, per-IP and per-route limits hold when per-key limits are dodged |
| `many_ips` | Rotating `X-Forwarded-For` (and real source addresses where the host has several) | Per-IP limits, and whether the gateway trusts forwarded headers it should not |
| `retry_wave` | Throttled clients retry at once, ignoring `Retry-After` (or honouring it, `honour_retry_after: true`) | Recovery under retries, and the difference that compliant clients make |
| `concurrency` | A burst of simultaneous new connections and in-flight requests rather than a rate | Connection and concurrency limits, accept queues |
| `slow_rise` | Rate rising slowly from under to over the limit | The exact rate where enforcement starts, compared with the configured limit |
| `limit_probe` | Binary search on the rate for one identity | The effective limit and window, measured, when the configuration is unknown |

The rate-limit analysis in the report (per layer and per identity, sampled up to a bounded number of
identities):

- requests admitted per window against the expected limit: over-admission and under-admission, per
  gateway node when the gateway exposes one (`Via`, or a configured response header);
- time to the first 429 and time to recovery after the test stops;
- rate-limit headers: whether `RateLimit` / `RateLimit-Policy` (the IETF draft), `X-RateLimit-*` and
  `Retry-After` are present, consistent with what happened, and counting down correctly;
- collateral damage: throttling and latency in other layers during the test;
- upstream protection: what reached the server nodes during the test (from the correlation layer),
  which shows whether the limiter shields the upstream or only rewrites responses.

### 6.4 Scale

`scale` says how big the run is, separately from the patterns that say how hard it pushes.

| Parameter | |
|---|---|
| `client_nodes` | A number (wait for that many before starting) or `auto` |
| `server_nodes` | Expected upstream nodes; the run waits for them and checks the gateway reaches each (well-known path, section 11) |
| `virtual_clients` | Cluster-wide, split across client nodes by capacity |
| `connections_per_client` | Connection pool per virtual client, which sets the number of connections the gateway sees |
| `max_rate_per_node` | Lower than the node cap, to keep clients well below saturation |
| `identities` | How many distinct keys or tokens to mint or use, per layer |

With `client_nodes: auto`, the leader compares the scenario's peak rate with the measured capacity of the
nodes it has. When it needs more, it emits a `scale_request` event (`{needed_client_nodes, reason}`) on the
run feed. If the cluster has a controller hook configured, it also POSTs the event there. The hook URL is
allowlisted like targets, and the request is signed with the cluster secret. A controller such as the
platform answers by provisioning pods that join. The run starts when the scale is met, or after
`scale_timeout` with a warning that it runs undersized. Rustybin never starts machines itself.

### 6.5 Live tuning

A running run can be tuned without stopping it.

`PATCH .../runs/{run}` takes:

- `rate_multiplier` (0 to 10, for the whole run or one layer);
- `pause` and `resume` (all layers or one);
- `hold` (freeze the pattern at its current point);
- `skip_stage` (jump to the next `then:`);
- `set` (change any pattern parameter of a layer, for example `heavy_user.pattern.burst: 1000`);
- `add_layer` and `remove_layer`;
- `faults` (change the preset or a behaviour).

The rules:

- Each change is validated against the same schema and caps as a new scenario.
- The leader applies it on the next cluster tick: heartbeats long-poll, so they return at once on a change.
- Each change is recorded in the run's timeline and audit log, so the report shows exactly when the
  approach changed and what it did.
- Changes are in the replicated snapshot, so they survive a failover.

### 6.6 One parameter model, three surfaces

The parameters are the source of control, and none of the surfaces can drift from the others:

- **Schema**: `GET /_rustybin/harness/schema` serves the JSON Schema of scenarios and live changes, with
  descriptions, units, defaults, minimums and maximums (the caps of this node).
- **API**: scenarios as JSON or YAML (`POST .../runs`), live changes (`PATCH .../runs/{run}`), a preview
  (`POST /_rustybin/harness/preview`: the expected rate per second per layer and the total, without
  sending anything), and saved scenarios (`GET/PUT/DELETE /_rustybin/harness/scenarios/{name}`, bounded,
  persisted with `RUSTYBIN_MOCKS_STATE_DIR`'s pattern).
- **MCP**: tool input schemas are built from the same JSON Schema (`create_run`, `update_run`,
  `preview_scenario`, `save_scenario`, `list_scenarios`, `list_patterns`).
- **UI**:
  - the scenario builder renders its form from the JSON Schema (vanilla JS, no build step, like the rest
    of `ui/`), with a YAML view of the same scenario;
  - a pattern preview chart from `preview`;
  - during a run, live controls: a rate multiplier slider, pause and hold per layer, skip stage, and edits
    to any pattern parameter.
- **Built-in scenarios**: YAML files under `src/harness/scenarios/`, embedded in the binary like `ui/`:
  `smoke`, `soak`, `ramp-to-target`, `breakpoint`, `spike-and-recover`, `pulse`, `burst`, and one per
  test in section 6.3. They are listed next to saved scenarios and are a starting point to copy and tune.
- **Parity test**: a unit test walks the JSON Schema and fails when a parameter has no description or
  bounds, or is missing from the MCP tool schemas. A browser check (`conformance/ui/`) fails when the
  builder does not render a field for every schema property.

## 7. Correlation

Each harness request carries:

| Header | Value |
|---|---|
| `X-Request-Id` | `<run>-<node>-<seq>`, deterministic, so gateway access logs join with the report |
| `traceparent` | W3C, one trace per request, so a gateway with tracing shows the same id |
| `X-Rustybin-Harness` | `v1; run=<run_id>; node=<node_id>; seq=<n>; vu=<k>; sent=<unix_ns>; sig=<hmac>` |

The signature is an HMAC over the other fields with a run key the coordinator derives and hands only to
cluster members. Server nodes count only authentic harness traffic, so stray or spoofed headers on a
shared instance never pollute a run.

**Server side** (the correlation layer on every data-plane route of a server node):

- records per run: arrivals by node and operation, upstream processing time, and what the gateway
  changed on the request. The client sends a digest of the headers and body it sent; the server compares
  them and records sampled header adds, removes and rewrites, plus body integrity;
- answers with `Server-Timing: rb;dur=<ms>` and `X-Rustybin-Served-By: <node>; run=<run_id>; sig=<hmac>`;
- samples captures into the inspector (1 in N plus every anomaly) instead of capturing every request, so
  a 20,000 rps run never fills the ring buffer or its feed.

**Client side** classifies every response:

| Class | How it is known |
|---|---|
| `upstream` | A valid served-by tag for this run |
| `gateway` | A response without the tag (a rate limit, auth failure, gateway 5xx, cached answer), broken down by status |
| `transport` | Connect, TLS, timeout, reset, protocol error, each counted on its own |
| `lost` (coordinator, after the run) | Sent, seen by no server, and no response or a transport error at the client: the gateway swallowed it |

**Latency breakdown**:

- `total`: client view;
- `upstream`: the server's `Server-Timing`;
- `overhead` = total minus upstream (gateway plus network, with no clock sync needed);
- with clock sync (section 9), `request_leg` and `response_leg` one-way times, reported with the sync
  error bound.

In loop-through on one node the clock is shared and the legs are exact.

**Logs**: with `RUSTYBIN_LOG_FORMAT=json`, every node logs harness events with `run_id`, `node_id`, `seq`
and `trace_id`, so logs from clients, servers and the gateway join on the same ids.

## 8. Fault injection

Client behaviours, each with a probability or rate, all bounded by the caps:

- connection churn (new connection per request, TLS handshake bursts), long-held keep-alive connections;
- abandoned requests (cancel after n ms), half-open connections, resets mid-body;
- slow request bodies (a bounded trickle), oversized headers near common limits, malformed JSON, wrong
  content types;
- retry waves (immediate retries on 5xx), synchronised bursts (synchronised bursts across all nodes at the
  same coordinator tick), credential churn (expired and revoked tokens);
- protocol mix (HTTP/1.1 and HTTP/2 against the same route), WebSocket connection bursts and SSE readers that never
  read (phase 7).

Server behaviours, applied by server nodes to authentic harness traffic only:

- the shaped endpoint `/harness/{*path}`: per-run latency distribution, status mix, body size, chunked
  or streamed responses, slow first byte;
- flapping health (`/health` toggled on a schedule), connection drops, stalls after headers;
- node churn: the coordinator tells a server node to stop accepting for n seconds or to leave and
  rejoin, which exercises the gateway's health checks and circuit breakers.

Presets: `calm`, `jittery`, `flaky-upstream`, `retries`, `synchronised`, `churn`, `all` (all of
them at once). A preset is just a named `faults` block; scenarios can override any field.

## 9. Cluster protocol

In steady state, nodes pull. They call the leader and the leader never calls them, so nodes behind NAT,
in other regions or on a private network all work. Only elections need node-to-node calls, and only
between eligible nodes (section 9.1).

Controller routes are answered by the leader. On any other node they answer
`307 Temporary Redirect` to the same path on the leader. The redirect carries
`X-Rustybin-Harness-Leader: <node_id>; term=<n>` and a JSON body naming the leader. A controller can
therefore talk to any node it knows and follow the redirect. Clients that do not follow redirects read the
body.

| Route | Who calls it | |
|---|---|---|
| `GET /_rustybin/harness` | anyone with control access | Node status: roles, cluster, current run, caps, `harness_api: 1`, and `leader: {node_id, control_url, term, since}` as this node sees it |
| `GET /_rustybin/harness/clusters/{id}/leader` | controller, any node | The leader, the term, the succession list with each node's work score, and the history of leader changes. Answered by every member (never redirected), so a controller can always find the leader |
| `POST /_rustybin/harness/join`, `/leave` | controller | Tell this node to join or leave a coordinator (orchestrated) |
| `POST /_rustybin/harness/stop` | controller | Kill switch: stop all local load now |
| `POST /_rustybin/harness/clusters` | controller | Create a cluster: `{cluster_id?, min_nodes?}` returns the id and a join token |
| `GET /_rustybin/harness/clusters/{id}` | controller | Members, roles, health, clock offsets, current run |
| `GET /_rustybin/harness/clusters/{id}/upstreams` | controller | Server nodes' advertised URLs as a plain JSON list, for configuring the gateway's upstream pool |
| `POST /_rustybin/harness/clusters/{id}/runs` | controller | Submit a scenario; returns `run_id` (validated, not started) |
| `POST .../runs/{run}/start`, `/stop` | controller | Start (synchronised) or stop |
| `PATCH .../runs/{run}` | controller | Live tuning (section 6.5) |
| `GET /_rustybin/harness/schema` | controller, any node | JSON Schema of scenarios and live changes, with this node's caps as bounds (section 6.6) |
| `POST /_rustybin/harness/preview` | controller, any node | Expected rate per second per layer for a scenario, without sending anything |
| `GET`, `PUT`, `DELETE /_rustybin/harness/scenarios/{name}`, `GET /_rustybin/harness/scenarios` | controller | Saved scenarios plus the built-in ones (read only) |
| `GET .../runs/{run}` | controller | Live merged stats |
| `GET .../runs/{run}/events` | controller | SSE feed of 1 s snapshots (the console reads it with `send({stream: true})`) |
| `GET .../runs/{run}/report` | controller | Final report (JSON; `?format=junit` or `text`) |
| `POST /_rustybin/harness/clusters/{id}/nodes` | node, join token | Join: `{node_id, roles, advertise, capacity, version}` returns a node credential and a lease |
| `POST .../nodes/{node}/heartbeat` | node, node credential | Long poll (up to 10 s): carries stats deltas, histograms, clock-sync stamps, the node's work report and its term; returns an assignment, a profile, `stop`, and the latest cluster state snapshot when its version changed |
| `POST .../election/vote` | eligible node, node credential | A candidate asks for a vote: `{term, candidate, snapshot_version}`; answer `{granted, term, leader?}` |
| `POST .../election/elected` | new leader, node credential | Announces the new term to eligible peers so they stop waiting; the other nodes learn on their next heartbeat |

- **Single node** is a cluster of one with the node as its own coordinator. `POST /_rustybin/harness/runs`
  is shorthand for that, so the simplest use needs no cluster at all.
- **Assignments**: the coordinator gives each client its share of the rate (by declared capacity), its
  range of virtual clients and credentials, the scenario hash, and a `start_at` in the node's own clock.
  Server nodes get the server profile and the run key.
- **Clock sync**: NTP-style timestamps on every heartbeat. The coordinator keeps an offset and an error
  bound per node, used for synchronised starts, synchronised ticks and one-way legs.
- **Leases, the dead man's switch**: a client stops sending if it has had no heartbeat answer from a
  leader for a lease period (default 5 s, renewed by any leader of the current or a newer term). An
  election finishes inside the lease, so a failover does not stop the load. A cluster that cannot elect a
  leader in time (a partition, too few nodes left) stops sending, and never leaves clients sending.

### 9.1 Leadership and failover

The coordinator role moves between nodes. One node leads at a time, everyone can see which one, and when it
dies the node doing the least work takes over and changes role.

**Who leads first**: the node started with the `coordinator` role (headless), or the node a controller
created the cluster on (orchestrated). It starts term 1.

**Everyone knows the leader**: the leader's id, control URL and term are in:

- every heartbeat answer;
- `GET /_rustybin/harness` on every node;
- `GET .../leader` on every member;
- the `X-Rustybin-Harness-Leader` header on redirects;
- the run's SSE feed (a `leader_changed` event).

**Replicated cluster state**: each node needs enough state to continue the run if it becomes leader, so
the leader replicates a versioned snapshot:

- membership and roles;
- the run, its scenario and stage, and each node's assignment;
- the succession list;
- the last merged totals and histograms (a checkpoint every 5 s);
- the run key, and the cluster secret that node credentials and join-token hashes derive from.

Every node gets the snapshot without the secrets. Eligible nodes also get the secrets: only they can lead,
and only they need to verify credentials. The snapshot is bounded in size (section 10) and sent only when
its version changes.

**Least work**: each heartbeat carries the node's work report:

- its assigned share of the rate;
- requests in flight and virtual clients;
- upstream arrivals per second (server role);
- CPU and scheduler lag.

The leader turns that into a work score and orders eligible nodes by it, ascending: the succession list.
`prefer` nodes (standbys) come first, so an idle standby coordinator is always the natural successor.
Ties break by node id, so the order is total. Because the list is in the snapshot, every node agrees on
the order without talking to the others.

**Election** (a Raft-style vote, with the candidate order fixed by the succession list instead of
random timeouts):

1. A node that gets no heartbeat answer for the election timeout (3 s) considers the leader gone.
2. The first live node in its succession list becomes the candidate. A node at position k waits
   k x 500 ms before standing, so position 1 normally wins without a contest.
3. The candidate raises the term and asks the eligible nodes for votes. A node grants its vote when it
   has also lost the leader, has not voted in this term, and the candidate's snapshot is at least as
   recent as its own. A node that still hears the old leader refuses. That prevents a false failover
   when only the candidate's own link is down.
4. With votes from a majority of the eligible nodes in the last snapshot, the candidate becomes leader
   and announces the new term. A candidate that fails gives way to the next position after its wait.
5. Non-eligible nodes keep heartbeating against the last leader and then fall back to the URLs in their
   snapshot's succession list until one answers with a newer term. They learn the new leader without
   voting.

**Changing role**: the new leader adds the `coordinator` role.

- By default (`leader_sheds_load: true` in the scenario) it hands its client share back. The rate is
  re-split over the remaining clients on their next heartbeat, so the cluster-wide rate stays as the
  scenario says.
- It keeps its server role. The gateway's upstream pool must not change because of an election.
- It resumes the run from the last checkpoint: it keeps the stage clock, and nodes report cumulative
  counters and histograms since the run started (not deltas since the last ack), so their first
  heartbeat to the new leader fills the gap exactly.
- The only data that can be lost is the dead leader's own client traffic since its last checkpoint. The
  report shows it as `unreported` with an upper bound, never silently.

**The old leader comes back**: every message carries the term. A node that sees a newer term steps down
at once: it drops the coordinator role, stops answering controller routes (redirecting instead) and
rejoins as an ordinary member. Its own requests are refused as stale until it does. No two leaders can act
in the same term.

**Two-node and one-node clusters**: a majority of two is two, so a two-node cluster cannot fail over. It
behaves like v1 without failover: the leases expire and the run stops. The plan says so in the docs, and
`GET .../leader` reports `failover: unavailable` until at least three eligible nodes have joined.

**Controller handover**: a controller watching the SSE feed gets `leader_changed`, then the stream
ends; it reconnects to the new leader's URL from the event. A controller holding only one node's URL
follows the redirect. The platform stores the cluster's eligible URLs and asks any of them.

## 10. Limits and bounded state

| Limit | Default | Notes |
|---|---|---|
| Rate per client node | 50,000 rps | `RUSTYBIN_HARNESS_MAX_RATE`; also cluster-wide in the scenario. Confirmed by phase 0: a safety cap, near what one client core can send; a node with more cores may raise it |
| In-flight per node | 10,000, and at most what the descriptor limit allows | Beyond it: `not_sent` plus a saturation flag. HTTP/1 holds one connection per request in flight, and in `both` mode each costs two descriptors (client and server side). At start the engine raises its soft `RLIMIT_NOFILE` to the hard limit and caps in flight at (limit minus 256) divided by 2 in `both` mode, or minus 256 on client-only nodes, and says so in the status and report. Running out of sockets is client saturation, never a gateway or transport result (phase 0) |
| Run duration | 1 hour | `RUSTYBIN_HARNESS_MAX_DURATION`, at most 24 hours |
| Nodes per cluster | 64 | at most 1,024 |
| Clusters per coordinator | 4 | |
| Runs kept per cluster | 20 | oldest dropped; idle TTL 24 hours |
| Timeline | 1 s buckets up to 1 hour, then 10 s | fixed upper bound per run |
| Samples per run | 1,000 | worst latencies, every class of error, gateway header changes |
| Per-run label values in metrics | active run plus the last 4 | `rustybin_harness_*` stays bounded |
| Body sizes, header sizes, slow-body trickle | capped like the other mock limits | |
| Cluster state snapshot | 1 MB | membership, assignments, succession and the last checkpoint; a snapshot over the cap refuses the change that grew it |
| Leader history | last 32 changes per cluster | for `GET .../leader` and the report |
| Election | timeout 3 s, 500 ms per succession step, at most 3 rounds | then the cluster stops sending (leases) |
| Layers per run | 8 | |
| Saved scenarios | 100 per node, 256 KB each | persisted when a state directory is set |
| Identities tracked in the rate-limit analysis | 1,000 per layer | the rest are aggregated |
| Live changes | 10 per second per run, the last 500 kept in the timeline | |
| Burst size | 100,000 requests, never above the in-flight cap times the client nodes | |

The client also measures itself: scheduler lag (intended versus actual send), event loop lag, CPU and
open sockets. When it saturates, the report says so first, so a slow client is never read as a slow
gateway. Saturation is judged per one-second bucket and needs two buckets in a row (phase 0 saw single
lag spikes in a VM that one bucket would misread), and the achieved rate is counted by completion time
in those buckets: dividing all answers by the run's elapsed time reads a 100 ms upstream as 3 percent
short over 3 s, since the last requests finish one latency after the window.

## 11. Safety

Load generation is the first time Rustybin sends load to targets a caller chooses, so the fences come
first and are tested first. (A2A push notifications already send single requests to caller-supplied URLs,
behind `RUSTYBIN_A2A_PUSH_ALLOWLIST`; the leads webhook and the key registry URL are operator-set. The
harness allowlist and verification follow the same idea at load scale.)

- Off by default; fatal with public mode or self-service (section 5). The hosted demo never enables it.
- **Target allowlist** on every client node (`RUSTYBIN_HARNESS_TARGETS`). Names are resolved, and the
  resolved addresses are checked and pinned for the run (no DNS rebinding). Link-local, metadata
  (`169.254.169.254`, `fd00:ec2::254`) and the node's own control plane are always refused. A node checks
  every assignment against its own allowlist, so even a compromised coordinator cannot aim it elsewhere.
- **Target verification** (`RUSTYBIN_HARNESS_VERIFY_TARGETS`, on by default in hosted mode): before a
  run, each target must serve the run's verification token at `/.well-known/rustybin-harness`, or
  publish it as a DNS TXT record at `_rustybin-harness.<host>`. Server nodes in the cluster answer that
  path themselves. A gateway that routes to them therefore passes automatically, which also proves the
  route reaches the cluster before a single load request is sent. This is what lets a platform offer
  harness runs without becoming a way to send load to third parties.
- **Authorisation**: a new control scope `harness`. The admin token and the `admin` scope imply it.
  The management MCP gets `Right::Harness`. Node routes accept only join tokens and node credentials,
  never control tokens. Join tokens and node credentials are compared in constant time and never logged.
- **Failover does not widen anything**: a new leader can only hand out assignments that every node still
  checks against its own allowlist, and an election never starts a run that was not running. Secrets go
  only to eligible nodes, over the authenticated node routes. Votes and announcements carry the node
  credential and the term. A node outside the last snapshot's membership can neither vote nor stand.
- **The kill switch reaches every leader**: `POST /_rustybin/harness/stop` on any node stops its own load
  and is forwarded to the leader. A stopped run stays stopped across a failover, because the stop is in
  the replicated snapshot.
- **Caps** (sections 9 and 10). Audit lines for cluster create, join, leave, run
  start and stop, kill, elections and leader changes, without scenario bodies or credentials.
- **Controller hook** (`scale_request`, section 6.4): off unless configured; its URL must be in the
  allowlist, the request is signed with the cluster secret, and it carries no scenario or credentials.
- **Live changes go through the same fences**: a `PATCH` is validated against the schema, the caps and
  every node's allowlist like a new scenario. A rate multiplier cannot lift a run above the caps.
- Credentials in scenarios (API keys, client secrets) are redacted in every read, report and log, like
  key redaction in captures.

## 12. Reports and metrics

The final report (JSON, plus `text` and `junit` renderings):

- run, scenario hash, nodes and roles, clock-sync quality, client saturation flags;
- leader changes: term, old and new leader, when, how long the cluster ran without a leader, the rate
  re-split, and any `unreported` traffic from the old leader. These events are also marked on the
  timeline, which shows what a failover did to the load;
- totals by class (`upstream`, `gateway` by status, `transport` by kind, `lost`, `not_sent`);
- latency percentiles (p50, p90, p99, p99.9, max) for `total`, `upstream`, `overhead`, and the legs when
  synced, overall and per target, operation, credential (consumer), client node and server node;
- every result per layer as well as in total;
- the timeline per stage and layer (rate achieved versus requested, latencies, classes), with pattern
  changes, live changes and leader changes marked on it, which shows where a rate limit or breaker
  kicked in and what each change did;
- the pattern results: the last good rate of a `breakpoint`, the time to recover from a `spike`, each
  `step`'s plateau, how far a `target` held from its goal;
- the rate-limit analysis of section 6.3 for layers with `expect`;
- what the gateway changed (sampled header adds, removes and rewrites, body integrity failures);
- thresholds with pass or fail and the measured value;
- samples with their `X-Request-Id` and `traceparent`, ready to look up in gateway logs.

Prometheus on every node: `rustybin_harness_requests_total{run,class,status}`,
`rustybin_harness_latency_seconds{run,kind}` (histogram), `rustybin_harness_inflight`,
`rustybin_harness_scheduler_lag_seconds`, `rustybin_harness_server_arrivals_total{run}`,
`rustybin_harness_term`, `rustybin_harness_is_leader`, `rustybin_harness_elections_total{outcome}`, with the run
label bounded (section 10). Reports can be kept on disk with `RUSTYBIN_HARNESS_REPORT_DIR`.

## 13. Surfaces

Every parameter is set the same way from the API, MCP and UI, from one schema (section 6.6).

- **Control API**: section 9, in the catalogue and OpenAPI like every route, with examples that run
  against a single-node loop-through.
- **Management MCP** (`src/mcp/manage/`):
  - tools: `harness_status`, `create_cluster`, `list_cluster_nodes`, `get_leader`, `export_upstreams`,
    `validate_scenario`, `preview_scenario`, `list_patterns`, `list_scenarios`, `save_scenario`,
    `create_run`, `start_run`, `update_run` (live tuning), `stop_run`, `get_run`, `get_run_report`;
  - input schemas come from the scenario JSON Schema, so a parameter added to the model is in the tools
    without further work;
  - every tool works on any node: the in-process call follows the leader redirect, and results name the
    leader that answered;
  - `start_run` sends real traffic to the outside world, so it gets `openWorldHint` and confirmation
    (elicitation, else `confirm: true`), like the destructive tools. So does `update_run` when it raises
    the rate or adds a layer;
  - `stop_run` needs no confirmation;
  - each tool has its `Right` and is filtered by role in `tools/list`;
  - prompts: `load_test_gateway` walks an agent through allowlist, scenario, preview, a dry run at a low
    rate, then the real run; `test_rate_limits` asks for the configured limits and builds the matching
    rate-limit test with `expect` set.
- **Console**: a Harness page, shown only when load test mode is on:
  - cluster members (role, health, clock offset, work score, succession position) and a leader badge
    with the term and its history;
  - the scenario builder generated from the schema: targets, scale, layers and their patterns, with a
    preview chart that redraws as parameters change, a YAML view, built-in and saved scenarios;
  - the run view: live charts per layer (rate requested and achieved, latency percentiles, classes,
    429s), and the live controls of section 6.5;
  - the report, with the rate-limit analysis and samples.
- **CLI**: `rustybin harness run | validate | report | coordinator` (section 5).

## 14. Platform integration (decoupled)

The platform needs nothing harness-specific from core beyond this API. A harness on the platform is just
Rustybin pods with harness env plus calls to one coordinator:

1. Provision: n client pods (`p1` for heavy runs), m server pods, and one coordinator pod. For failover,
   two small standby pods with `RUSTYBIN_HARNESS_LEADER=prefer` give a successor that does no other work.
   Each pod gets `RUSTYBIN_HARNESS_*` env (with `RUSTYBIN_HARNESS_CONTROL_URL` = its pod URL, so it is
   eligible), and the join token as a pod secret, the same allowlisted `pod.secrets` path as
   `RUSTYBIN_ADMIN_TOKEN`.
2. Configure the customer's gateway upstream pool from `GET .../upstreams` (customer action, or their
   automation).
3. Drive runs with a platform-issued control JWT carrying the `harness` scope. The platform keeps the
   eligible pod URLs and calls any of them; redirects and `GET .../leader` take it to the current leader,
   so it never has to track failovers itself.
   With `client_nodes: auto`, the platform registers itself as the controller hook and answers
   `scale_request` events by provisioning more client pods, which join on their own.
4. Collect the report into insights; meter run hours with the existing load-test hours meter, or a new one.
5. Tear down: delete the pods. Leases make sure nothing keeps sending if teardown is late.

Platform rules (outside this repo): `RUSTYBIN_HARNESS_VERIFY_TARGETS` always on, targets limited to
verified customer domains, rate caps per plan, and a run cap per org. The platform side gets its own plan
in `rustybin-platform` (job kinds such as `harness_provision` and `harness_teardown`, the contract
additions, UI).

### Phase 0 results (2026-10-25)

load), release build, `GET /status/200`, HTTP/1.1, the client on its own runtime plus the scheduler

| Upstream | Server threads | Client threads | Sustained rps | Requests per CPU second (client and server) |
|---|---|---|---|---|
| Rustybin | 1 | 1 | 20,000 | about 12,000 |
| Rustybin | 2 | 1 | 25,000 to 30,000 | about 10,000 |
| Rustybin | 3 | 1 | 30,000 | about 8,800 |
| bare | 2 | 1 | 30,000 to 50,000 | about 16,000 to 25,000 |
| bare | 1 | 2 | 25,000 to 75,000 | about 13,000 to 26,000 |

Ranges are repeated sweeps of the same configuration: on four cores with five busy threads the
scheduler is sometimes preempted, and a single lag spike ends a sweep early. Latency p50 stays under
0.5 ms up to the sustained rate; p99 has isolated spikes of 30 to 70 ms from the same contention.

What it shows:

- **The client is cheap; Rustybin's own data plane is the cost.** The client and a bare server together
  use about 40 to 60 us of CPU per request, so the client, about half of that, sends roughly 30,000 to
  50,000 rps per core.
  In loop-through Rustybin uses about 115 us per request, about 90 us of it on the server side, which
  is the full middleware stack (inspector capture, metrics, trace, CORS, limits, fault injection) on a
  trivial route. A 4-core loop-through node therefore tops out near 30,000 rps, a server node near
  10,000 to 15,000 rps per core. Profiling the data plane is worth a session before scale tests; phase 2's
  inspector sampling removes one of the costs for harness traffic.
- **Saturation detection works** at real rates: past the sustained rate the in-flight cap fills, the
  requests are counted as `not_sent`, and the run is flagged instead of slowing down (two tests in the
  example check it against a stand-in upstream).
- **Descriptors are the first hard limit.** 2,000 requests in flight against a 100 ms upstream ran
  cleanly with 20,000 descriptors; with 1,024 (a common default) 45,272 of 60,000 requests failed and
  some waited out the 10 s timeout. Hence the in-flight rule in section 10. HTTP/2 to the target
  multiplexes requests over few connections and avoids it.
- **The scheduler needs its own thread** (section 4) and `TCP_NODELAY` on every connection; a fresh
  connection pool per run showed up as p99 spikes, so pools live as long as the run's targets.
- **Caps** (section 10): 50,000 rps per client node confirmed; the in-flight cap now also follows the
  descriptor limit. The 1-hour duration, bucket and sample limits are unaffected by these numbers.

### Phase 2 build notes (2026-10-25)

What phase 2 built, and where it differs from sections 7, 8 and 12:

- **Headers**: `X-Request-Id: <run>-<node>-<seq>`, a `traceparent` (trace id from the run, node and
  sequence; span id from the sequence) and the marker `X-Rustybin-Harness: v1; run; node; seq; vu;
  sent=<unix ns>; h=<header names the client set>; hd=<digest of those headers>; b=<body digest>;
  p=<method and path digest>; sig=<HMAC-SHA256, 128 bits>`. The run key is random per run, held by the
  run and registered with the node's `Correlator` (a cluster's leader hands it to server nodes in phase
  3). Markers with an unknown run, a bad shape or a bad signature are served as ordinary requests and
  counted as `rejected_markers` (status and report).
- **Server layer** (`correlate::layer`, in `build_app` outside inspector capture): per run it records
  arrivals by node and route (bounded), statuses, processing time, and what the gateway changed: listed
  headers with other values (`headers_changed`), listed headers that did not arrive (`headers_missing`,
  by name), headers that arrived unlisted (`headers_added`, by name; `host`, `content-length` and the
  harness headers are never listed), body and path digests. The client's header digest covers the
  headers it set, the server recomputes it over the same names, so a rewrite is seen without sending
  per-header hashes. Answers get `Server-Timing: rb;dur=<ms>` and `X-Rustybin-Served-By: <node>;
  run; seq; t=<arrived ns>,<done ns>; sig`. The layer samples captures into the inspector (`servers.
  capture_sample`, 1 in N, default 100, plus every anomaly: a change, a missing header, a 5xx);
  the inspector honours the decision through a request extension.
- **Classes**: `upstream` (a valid tag of this run and sequence), `gateway` (an answer without one,
  by status in `gateway_statuses`), `transport` (by kind). `lost` is counted after the run: the server
  side keeps a per-run bitmap of the sequence numbers it saw (bounded to 2^26, `seen_overflow`
  above), the client keeps the sequence numbers of its transport failures (bounded to 2^20), and a
  failure the server never saw is lost; one it did see is `transport_after_upstream`. Without a server
  side on the node (a client-only node), `lost` stays 0 and `upstream_reach` cannot pass; phase 3
  merges the server nodes' views. Phase 1's `ok` / `unexpected_status` stay next to the classes: one
  says whether the status was the expected one, the other who answered.
- **Latency**: `upstream_latency` (the server's processing time), `overhead` (actual-send latency
  minus processing, for tagged answers), and in loop-through the `request_leg` and `response_leg`
  (the tag carries the server's arrival and completion times; legs are measured when the answering
  node is this node, one clock). Per bucket: `upstream`, `gateway`, `upstream_p99_ms`,
  `overhead_p99_ms`. New thresholds: `gateway_overhead_p99_ms`, `lost`, `upstream_reach`.
- **Metrics** (section 12): `rustybin_harness_requests_total{run,class,status}`,
  `rustybin_harness_latency_seconds{run,kind}` (total, service, upstream, overhead),
  `rustybin_harness_scheduler_lag_seconds{run}`, `rustybin_harness_inflight{run}`,
  `rustybin_harness_server_arrivals_total{run}`; the run label is bounded to the active run plus the
  last 4. The engine feeds them once per second from the roll, not per request.
- **Shaped endpoint** `/harness` and `/harness/{*path}` (any method): the scenario's `servers` block
  (`latency: {p50, p99}` as a log-normal, `status` weights, `body_bytes`, `chunked`,
  `first_byte_delay`, `capture_sample`) is registered with the run; a marked request of that run gets
  it, anything else the default (200, 256 bytes). Node churn and flapping health are phase 7.
- **Test proxy** (`src/harness/test_proxy.rs`, tests only): an axum server in front of the node that
  adds, removes and rewrites request headers, strips response headers, delays, answers every n-th
  request itself and swallows every n-th; the rate limiters come with phase 5. The tests check that
  every class and `lost` are counted exactly against its counters, that the overhead matches its delay,
  that a stripped tag reads as `gateway`, that a rewritten path and removed headers are reported, that
  spoofed markers are rejected, that sampling holds, and that the shaped endpoint follows its profile.

### Phase 3 build notes (2026-10-26)

What phase 3 built, and where it differs from sections 5, 9 and 10:

- **Files**: `cluster.rs` (the leader: `Coordinator` with the clusters this node leads, `Cluster` with
  members, runs and a version that wakes long polls, `ClusterRun` with the split, the merge and the
  report), `member.rs` (the agent on every member: join, heartbeat loop, lease, clock estimate, starting
  its assignment, answering the `lost` lookup), `wire.rs` (join, heartbeat and assignment shapes),
  `cluster_tests.rs` (several `start_with_state` servers in one process).
- **Who leads**: creating a cluster needs the `coordinator` role. The node it was created on leads it,
  term 1, with no failover (`failover: unavailable` in `GET .../clusters/{id}`). A coordinator that also
  has the client or server role joins its own cluster over an in-process link (no HTTP), so one node can
  be a whole cluster. A node is a member of one cluster at a time and leads at most 4.
- **Credentials**: only the join token's SHA-256 is kept. A node credential is an HMAC of the cluster
  secret over cluster, node id and a per-join incarnation, recomputed on every heartbeat, never stored.
  A rejoin with the same node id replaces the old member. The node routes (`.../nodes`,
  `.../nodes/{node}/heartbeat`, POST only, `harness::is_node_path`) skip the control-plane auth, the key
  layer and the plan limits: the token and the credential are their authentication.
- **Heartbeats**: a long poll of up to 10 s (capped below the time-to-headers timeout) that the leader
  answers at once when the cluster version changes; while a node sends load it heartbeats every lease /
  4 (100 ms to 1 s) with `wait_ms: 0`. Stats are **cumulative** from the start (the leader replaces the
  node's last stats, so a lost or repeated heartbeat never double counts); only timeline buckets the
  leader has not acknowledged travel. Histograms go as exact bucket lists (varint deltas, deflate,
  base64; bounded on decode), so the merge equals a merge in one process.
- **Clock**: NTP-style stamps on join and every heartbeat; the node keeps the 8 latest samples and uses
  the one with the shortest round trip (offset, half the round trip as error bound) and reports it to
  the leader. The synchronised start is `now + 4 x worst error + 300 ms`, clamped to 0.5 to 5 s, sent
  on the leader's clock and converted by each node.
- **The split**: by declared `max_rate` (capped by `scale.max_rate_per_node`), as cumulative intervals
  `[from, to)` of 0 to 1 (`engine::Share`). Rates scale by the fraction; closed-model users and virtual
  clients use cumulative rounding so the nodes' users add up to the pattern exactly and their virtual
  clients are disjoint ranges. Submitting validates one share against the leader's caps; starting
  refuses (409) when a node's share is over its cap or the quorum is missing. Each node validates its
  part against its own caps and pins targets against its own allowlist; a refusal shows as a `failed`
  node in the report.
- **Lost, cluster-wide**: when every client has sent its final stats (or is gone, or a deadline passed),
  the run goes to `collecting`: the leader sends each server node the failed sequence numbers per client
  node (at most 65536 per node, the rest `untracked`) and each answers which it saw. The report's
  `cluster.lost_check` says `complete` or why `lost` is a lower bound.
- **Verification**: a cluster has its own verification token. Members serve it at
  `/.well-known/rustybin-harness` and clients verify targets against it, so a gateway routing to any
  server node of the cluster passes.
- **Redirects**: controller routes asked on a member that does not lead the cluster answer `307` with
  `Location`, `X-Rustybin-Harness-Leader: <node>; term=1` and a JSON body naming the leader.
- **Shutdown**: a member leaves on shutdown (its runs stop, the leader marks it `left`) and the leader
  releases held heartbeats, so a graceful shutdown never waits for a long poll.
- **Not built yet**: `GET .../leader`, elections and terms (3b); the run's SSE feed, `PATCH`, preview and
  saved scenarios (phase 4); the CLI `coordinator` subcommand (headless env covers it); an MCP
  `get_leader` tool (3b). MCP gained `create_cluster`, `list_cluster_nodes`, `export_upstreams`,
  `start_run` and an optional `cluster_id` on `create_run`, `get_run`, `stop_run`, `get_run_report`;
  the console a cluster card (members, health, clock offsets, upstreams, create, run on the cluster).
- **Tests**: join and wrong tokens, quorum and the split (1:3 capacities give 50 / 150 of 200 requests,
  disjoint virtual clients), the merged totals equal to the nodes' and the test proxy's counts (now a
  round-robin pool over two server nodes) with `lost` exact, upstream export, redirects, lease expiry
  stopping the only client within the lease after the leader is gone, an assignment outside a node's
  allowlist, headless `on-quorum`, env parsing, and the MCP tools on a one-node cluster.

### Phase 3b build notes (2026-10-26)

What phase 3b built, and where it differs from section 9.1:

- **Files**: `election.rs` (the leader's ticker: runs, checkpoints, the quorum check, probing for a newer
  leader; promotion from a snapshot; stepping down), the candidate and voter rules in `member.rs`
  (`stand`, `vote`, `elected`, `not_leader`, `join_redirect`), the snapshot, succession and re-split in
  `cluster.rs`, the protocol types in `wire.rs` (`Snapshot`, `VoteRequest`, `ElectedRequest`, `NotLeader`,
  `WorkReport`), `test_net.rs` (tests: partitions that refuse or drop calls) and `failover_tests.rs`.
- **Eligibility**: a node with `RUSTYBIN_HARNESS_CONTROL_URL` (`auto` is the listener's address when it
  binds a specific one) and `RUSTYBIN_HARNESS_LEADER` other than `never`. The leader is always a member
  of its own cluster (in process) and counts among the eligible nodes; a coordinator-only node with a
  control URL and `RUSTYBIN_HARNESS_JOIN` joins as a standby. Eligibility is declared at join: a join
  token holder that declares a control URL gets the snapshot's secrets (the trust model is the join
  token, as before).
- **Snapshot and checkpoints**: versioned `(term, seq)`; the public part (leader, term, eligible nodes,
  succession, history) goes to every node, the state (members with incarnations, every run that has
  not finished with its scenario, key, assignments and a checkpoint of the stats, the cluster secret,
  the join token's hash, the verification token) to eligible nodes only. A checkpoint is a new version
  every 5 s, or every lease when shorter, while a run is active; the snapshot is built when sent, so it
  holds the freshest stats. Counters travel for every client part, histograms and failures only for the
  parts that will not report again (the leader's own, silent nodes). Finished reports stay on the node
  that led the run (and in `RUSTYBIN_HARNESS_REPORT_DIR`).
- **Succession and work**: live eligible members, `prefer` first, then by work score (the rate a node
  is assigned + arrivals per second + requests in flight + 100 per busy CPU core + 1 per millisecond of
  scheduler lag p99), then by node id; recomputed on joins, starts and checkpoints. Silent nodes leave
  the line but still count for the majority.
- **Timing**: the election timeout `E` is per cluster (`election_timeout` on create, default
  `RUSTYBIN_HARNESS_ELECTION_TIMEOUT`, always below the lease). Idle long polls last at most `E/3`,
  active nodes heartbeat every `min(lease/4, E/3)`, a heartbeat counts as unanswered after its wait plus
  `E/2`. Position `k` stands at `E + k x E/6` after the last answer (the plan's 500 ms at `E` = 3 s).
  Votes are counted as they arrive, so a silent voter never delays a won election; members look for the
  new leader by asking every node of the succession at once. In tests with a 2 s lease and `E` = 600 ms,
  the failover finishes well inside the lease, also when the old leader drops packets.
- **Votes**: granted when the candidate's term is newer, the voter has not voted for another candidate
  in it, it has not heard the leader for `E/2`, and the candidate's snapshot is at least as recent. The
  leader itself always refuses. A majority of the eligible nodes in the snapshot wins; the winner
  announces the term to the eligible nodes; the others learn it from any node they ask (a member
  answers a heartbeat with `409` naming its leader).
- **Check quorum**: with three or more eligible nodes, a leader that has not heard a majority of them
  within `E` answers heartbeats with `503` (no lease renewal), so the minority side of a partition stops
  sending, and asks the eligible nodes every `E/2` whether a newer leader exists; it steps down when one
  does. A node that sees a newer term in a heartbeat or an announcement steps down at once.
- **Load across a failover**: nodes report everything again to a new leader (cumulative stats; timelines
  in parts of 600 buckets). The new leader hands its own client share back (`scale.leader_sheds_load`,
  default true) only once another client node, not the old leader, has reported to it, and stops its own
  part before the re-split is visible: the cluster never sends more than planned (a dip of at most one
  heartbeat). A client part silent past its lease plus a heartbeat is gone and its share re-split (the
  phase 3 behaviour without failover lost that share for the rest of the run).
- **Unreported**: for a client part without final stats from its node, `unreported` is an upper bound:
  its rate since its last stats until it surely stopped, plus one second (counters are rolled up once per
  second), plus what it had in flight; the run fails with the bound in the error, never silently.
- **Not built**: a leader transfer on purpose (open question 1); the `leader_changed` SSE event (the feed
  comes with phase 4); MCP tools do not follow redirects in process (they name the leader instead). A
  crashed leader that restarts is a new node: restarted as a standby with `RUSTYBIN_HARNESS_JOIN`
  pointing at any eligible member, it is sent on to the leader.
- **Tests**: the least loaded eligible node takes over within the lease while the clients keep sending,
  with the old leader dropping packets; a `prefer` standby wins over an idle node with a lower id; the old
  leader's own part is reported up to its checkpoint and the rest within the `unreported` bound; the old
  leader steps down and redirects controllers when it returns; a minority partition stops sending while
  the majority carries on; a two-node cluster stops on leader loss; a node joins through a member that
  does not lead; the snapshot round trip (state for eligible nodes only, secrets out of `Debug`, a stop
  survives, credentials stay valid, a newer term makes a leader stale). A real `kill -9` of the leader of
  a five-process cluster: the standby led after about 3.5 s, the clients never stopped, the report
  counted 2000 of 2000 requests with `unreported` 0.

### Phase 4 build notes (2026-10-26)

What phase 4 built, and where it differs from sections 6.2, 6.4 and 6.5:

- **Files**: `pattern.rs` (every pattern of section 6.2 compiled into stages with an exact value and
  integral, jitter and phase), `live.rs` (the `Change` of a `PATCH`, the `Controls` every node applies
  on top of the scenario, the `LiveView` the scheduler evaluates, the stage log, the closed loops),
  `saved.rs` (saved scenarios), the `PATCH`, preview, saved scenario and feed routes in `api.rs`, a
  capacity per second in `test_proxy.rs` (503 over it), and `live_tests.rs` (every pattern followed
  second by second, a burst's window at the gateway, a breakpoint at the proxy's capacity, live changes
  and the feed, a hold in the report, `client_nodes: auto` with the hook, saved scenarios and the
  preview).
- **Patterns**: as in section 6.2, with these names: `constant`, `burst` and `wave` last `for`; `step`
  takes `hold` as extra time at the last plateau; `target` takes `overhead_p99_ms` (not
  `overhead_p99`), and `start` and `max` for its loop; `breakpoint` takes `every` (the plateau length),
  `growth` as a fraction per plateau and `until` with `error_rate`, `latency_p99_ms` and
  `overhead_p99_ms`. A chain has at most 16 stages. `burst`, `breakpoint` and `target` on a rate or the
  overhead need the open model, `target` on users the closed one. `limit_test` is phase 5, `replay`
  later.
- **The cluster clock, not a leader tick**: every node evaluates the same compiled pattern on the
  synchronised run clock of phase 3, so the nodes switch at the same instant without a tick from the
  leader; the leader only distributes changes and loop decisions (`Controls`, versioned). `jitter`
  varies the value once a second, seeded by run and layer (and node with `sync: node`), so every node
  draws the same values under `sync: cluster`; `sync: node` also shifts a periodic pattern by the node's
  place in the split (the start of its share), which spreads pulses, bursts and waves over the period.
- **Scheduler**: the open model sends from the integral of the rate (a credit that reaches one sends a
  request), in steps of at most 10 ms that never cross an edge of the pattern, so a curve that climbs
  from zero and a burst of `size` within `within` are followed exactly (tests: every pattern within 2
  percent or 2 requests per second; 200 requests within 100 ms reach the proxy within 160 ms).
- **Closed loops** read the per-second results of the whole run (all layers together: per-layer
  per-second results would need per-layer timelines on the wire), run by the engine on a single node and
  by the leader on the merged complete seconds of a cluster. `breakpoint` judges a plateau when it ends,
  leaving out its first second, and stops the run at the first that fails, with a finding that names the
  last good rate. `target` on overhead multiplies the rate by goal over measured, clamped to 0.8 to 1.25,
  every second, and reports a finding once the overhead stays within 10 percent of the goal for 3
  seconds; it needs answers tagged by a Rustybin server (section 7).
- **Live changes**: `layer`, `rate_multiplier`, `pause` / `resume`, `hold`, `skip_stage`, `set` (paths
  `<layer>.pattern.<field>`, `then.` for the next stage, or the whole `<layer>.pattern`; a pattern's type
  cannot change), `add_layer`, `remove_layer`. `faults` comes with phase 7. Times are on the run clock
  (the leader's for a cluster), so a hold freezes the same point on every node. The controls travel in
  heartbeats (to nodes behind the version) and in the snapshot; a node checks them against its own caps
  and stops its part when they are over. The log keeps the last 64 changes, at most 32 findings.
- **Stages in the report**: a stage log notes which stage and part each layer runs, with the controls in
  effect then, every 100 ms on a single node and every tick on the leader (and on every change), so a
  hold stretches a part and a skip cuts one short in the report. It is bounded (1000 marks) and in the
  snapshot. Like the loops, a stage's numbers are the run's, all layers together.
- **Scale**: `client_nodes: auto` compares the run's peak with the declared capacity of the live client
  nodes (`RUSTYBIN_HARNESS_MAX_RATE`, or `max_rate_per_node` when lower), not a measured one. The hook
  is node configuration (`RUSTYBIN_HARNESS_SCALE_HOOK`, on every node that may lead), allowlisted and
  pinned like a target, one POST per request (5 s timeout, no retry), signed with HMAC-SHA256 keyed with
  the join token's SHA-256 in hex: a controller knows the token, not the cluster's internal secret, and
  the hash is in the snapshot, so a new leader signs the same way. `scale_timeout` is 5 minutes by
  default, at most 1 hour. `connections_per_client` sets the keep-alive pool per target (the node's
  virtual clients times it, within the in-flight cap). `identities` is phase 6.
- **Preview**: each layer's and the total expected requests per second from the pattern math (the exact
  integral over each second; closed layers show users), without jitter, at most 3600 points (coarser
  past an hour). `POST /_rustybin/harness/preview` works with the harness off, like `validate`.
- **Saved scenarios**: per node and not replicated, at most 100, validated against the node's caps, not
  under a built-in's name; files under `RUSTYBIN_HARNESS_STATE_DIR/scenarios`.
- **The feed**: `GET .../runs/{run}/events` (server-sent events): `snapshot` every second, `change`,
  `finding`, `finished`, and `leader_changed` and `scale_request` on a cluster run. The console reads it
  with `send({stream: true})` and falls back to polling.
- **Surfaces**: MCP tools `list_patterns`, `preview_scenario`, `save_scenario` and `update_run`
  (confirmation when a change may raise the load); in the console, the preview chart, saved scenarios
  with Save as, the live controls and the report's changes, findings and stages.
- **The roll has its own thread**: since phase 1 the scheduler merged the shard histograms into the
  timeline itself, once a second, and sent nothing meanwhile (1 to 3 ms in a release build, about 20 ms
  in a debug build, enough to read a slow debug run as saturated). A roller thread per run now takes
  each second's counters and lag over a bounded queue, merges, and runs the closed loops; the scheduler
  waits for it only at the end, before the report. Layer slots kept free for `add_layer` are skipped
  when nothing was recorded in them.

### Phase 5 build notes (2026-10-28)

What phase 5 built, and where it differs from section 6.3:

- **Files**: `limit_test.rs` (the `limit_test` pattern: its parameters, the stages each test compiles
  into, what the engine adds while it runs, validation, schema), `ratelimit.rs` (the rate-limit headers,
  the accumulator, the analysis and its text), reference limiters in `test_proxy.rs`, `limit_tests.rs`
  (every done-when test of section 15, the analysis around them, and a cluster run).
- **`expect`** on a layer: `limit` per `window`, `per` (`key` by default), plus `burst` (a token
  bucket's allowance: over-admission counts from limit plus burst), `status` (the refusal statuses,
  429 by default; `Counts.limited` and `Bucket.limited` count them for every layer) and `node_header`
  (a response header naming the gateway node). A `limit_test` without `limit` or `window` takes the
  layer's `expect` (filled in by `normalise`, and for `add_layer`).
- **Layer thresholds live on the layer** (`layers[].thresholds: {rate_limited, over_admission,
  under_admission}`), not under `thresholds.layers.<name>` as section 6's example has them: they travel
  with the layer (`add_layer` too) and the console builder renders them without a map editor. They
  report as `layers.<name>.<threshold>`.
- **The tests' parameters**: `factor` (`over_limit` 10, `distributed` 4, `many_keys` and `many_ips` 5,
  `retry_wave` 3), `fraction` (`just_under`, 0.9), `for`, `cycles` (3), `size` (the limit), `within`
  (a tenth of the window, at most 100 ms; 10 ms for `concurrency`), `every`, `identities` (20),
  `header`, `retries` (3), `honour_retry_after`, `retry_delay`, `from` / `to` / `over` (`slow_rise`),
  `min` / `max` / `steps` (`limit_probe`), `align` (`clock` or `start`) and `recover` (after the
  test, half the limit for that long, to measure the recovery). Validation names a parameter a test does
  not take. A limit test needs the open model.
- **`window_edge` bursts at every other boundary**: with a burst on each side of every boundary, each
  fixed window holds an after-burst and a before-burst and refuses the second, so nothing doubles. The
  stage's period is two windows (shape `edge`): one burst `within` ending a quarter of `within` before
  an even boundary, one starting as long after it. `window_edge` and `distributed` stages are aligned
  to the wall clock (`Stage.aligned`, `Ctx.wall`, the run's Unix start time, a cluster's synchronised
  start on every node); holds and skips are not followed by the alignment.
- **Identities are a simple pool** for `many_keys` and `many_ips` only: the request's identity is its
  layer sequence number modulo `identities`, `{{id}}` and `{{ip}}` (198.18.0.0/15, RFC 2544) are
  placeholders for every layer (0 and 198.18.0.0 outside a pool), and `many_ips` sets the forwarded
  header unless the template does. `many_keys` must use `{{id}}`. Real source addresses are phase 6.
- **`retry_wave`**: a refused request is retried with a new sequence number, the same identity and
  target, at once (`retry_delay`) or after its `Retry-After` (at most 60 s). Retries count in the
  layer's sent and in flight while they wait, and are dropped once the scheduler stops (no load after
  the patterns end).
- **`limit_probe` is a closed loop** like `breakpoint`: the probe stage is `closed`, the loop halves
  the range every `every` (whole seconds, at least 2 s), judging the probe's second half on the run's
  refusals per second (`Bucket.limited`, all layers: run it on its own), and reports the highest rate
  without a refusal as a `limit_probe` finding. The run's leader runs it on a cluster.
- **The analysis counts by send time** in cells of a twentieth of the window (10 ms to 1 s) on a grid
  whose windows start on the wall clock (or at the layer's start with `align: start`), at most 36 000
  cells per layer. Over-admission is the worst window-long span (to within a cell) over limit plus
  burst, as a fraction of the limit; under-admission the mean shortfall in windows that sent more than
  the limit. The measured window is the median spacing of admission resuming after refusals (a limiter
  that refills all at once). The first 64 identities, 16 gateway nodes (targets, or `node_header`
  values) and 3600 windows each are followed one by one. Collateral damage looks at the layers without
  a limit test during the test stages' planned times; recovery at the `recover` stage.
- **Headers**: `RateLimit` in every IETF draft form (`limit=, remaining=`, `r=` with
  `RateLimit-Policy: q=`, and `RateLimit-Limit` / `-Remaining` / `-Reset`), `X-RateLimit-*` and
  `Retry-After` (seconds or a date). Whether the remaining count counts down is judged on completion
  order, worker by worker, for layers with one identity.
- **Upstream protection**: the marker carries the layer index (`l=`, signed), the server side counts
  arrivals by layer (`ServerReport.by_layer`), and the analysis compares what reached it with what was
  admitted: more is a limiter that forwards and rewrites the answer. Refusals that carry the run's
  served-by tag were made by the upstream itself (`limited_by_upstream`) and are said so, not counted
  against the gateway.
- **Clusters**: each client node counts its own answers; the counters travel in the final stats only
  (`NodeStats.limits`) and the leader merges them before the analysis, so a node that never delivered
  its final stats is missing from it (as `unreported` says).
- **Workers buffer observations** (at most 65 536 between two rolls; more are counted as dropped) and
  the roller thread counts them into the run's accumulators: a per-worker accumulator indexed by run time
  would grow with the run on every roll.
- **Surfaces**: the schema (the `limit_test` variant, `expect`, layer `thresholds`, the placeholders),
  so `list_patterns`, the MCP tool schemas and the console builder have them; the report's
  `rate_limits` and its text section; the analysis in the console's report and in the MCP
  `get_run_report` summary; built-ins `rate-limit`, `limit-probe` and `many-ips`. No new routes.

### Phase 6 build notes (2026-10-28)

What phase 6 built, and where it differs from sections 6 and 12:

- **Files**: `mocksource.rs` (a mock source resolved into a plan), `identity.rs` (the identities of a
  layer), `breakdown.rs` (per-operation and per-credential results), `sample_request_variant` in
  `mocks/checks.rs`, `traffic_tests.rs`; a test proxy that records a header and its peers' addresses.
- **Mock sources** take the plan's flat form (`source: { mock, operations, invalid_fraction }`) plus
  `operations.include` and `weights`, `stateful` and `base_path` (default `/mock/<name>`, empty when
  the gateway maps the mock's own paths). Each client node resolves the mock from its own live revision
  when the run starts (not from the coordinator): every client node needs the mock, which file-defined
  mocks (`rustybin.yaml`) give. A layer sends at most 64 operations.
- **Requests**: four variants per operation (the sample with examples first, then three generated from
  the schemas with their own seeds), picked by weight with the sequence number hashed (splitmix64), so a
  short run sees every operation. An invalid variant where the operation has one: a body of the wrong
  type, a required query parameter left out, or a numeric path parameter that is not a number; it
  expects any 4xx, and the report says how many were not refused (mocks validate in `warn` mode by
  default: an unvalidating path answers them 2xx).
- **Create then read**: a POST on a collection whose GET on the item exists is followed, when it
  succeeds, by that GET with the id from the answer (`id`, the path parameter's name, or a field ending
  in `id`; the answer's first 64 KB are kept for it). The read is a new request of the layer. Item
  operations of a stateful source accept a 404 (ids nobody created).
- **Identities live on the layer** (`identities`), not in `scale`: `count`, `api_keys` (header or
  query; `values`, or `mint` named `<prefix><n>`, so the gateway can be provisioned with the same
  names), `jwt`, `oauth`, `forwarded`, `source_addresses`. Identity `n` takes the `n`th of each pool;
  a request takes the next identity in turn (the layer's sequence number), not its virtual client's;
  a limit test's pool comes first. Identity headers replace a template's headers of the same names.
- **JWTs** are signed by the client node's IdP key (RS256, the node's own key and JWKS: a cluster's
  nodes sign with different keys) or the demo HS256 secret (the same everywhere), lazily, one per
  subject, reused until 30 s before they expire. The default issuer is `rustybin-harness`.
- **OAuth client credentials** (`client_secret_post`): the token URL is allowlisted and pinned like a
  target, every client's first token is fetched before the run (a failure refuses the run with 422),
  then cached and fetched again before expiry, one fetch at a time per client. A token that cannot be
  had mid-run sends the request without it and is a warning in the report.
- **Source addresses** must be this host's (checked by binding when the run starts); each target gets
  a client per address, connecting to the target's addresses of the same family.
- **Added layers** (`add_layer`) take mock sources and every pool but `oauth` and
  `source_addresses` (refused: they are set up when the run starts). There is no live `identities`
  change: section 6.5 does not list one.
- **Breakdowns** (`report.operations`, `report.credentials`): answers, OK, errors, refusals and the mean,
  with p50 and p99 from a 64-bucket log histogram (about 25 percent wide) rather than exact ones; at
  most 256 keys per layer and kind (then `other`), 64 shown per layer. Invalid requests and reads after a
  create are their own rows. Credential labels carry no secret: the minted key's name, `key <n>` for a
  listed key, the JWT subject, the OAuth client id, the address. The rate-limit analysis still follows
  the first 64 identities, not the 1,000 of section 10. Final stats carry the breakdowns and the
  warnings; the leader merges them.
- **Redaction**: listed API keys and client secrets join credential-looking headers as `[redacted]` in
  reports. Saved scenarios keep them, like header values (they are the operator's configuration).
- **Console**: the builder no longer gives `method` (or other enums inside optional objects) a default,
  which made an untouched request template sit next to a mock source; the builder check opens collapsed
  sections before clicking an add button.

### Phase 7 build notes (2026-10-28)

What phase 7 built, and where it differs from section 8 and the protocol sources of section 6:

- **Files**: `faults.rs` (the `faults` block, presets, draws, schema), `protocols.rs` (the `llm`, `sse`,
  `websocket`, `grpc` and `mcp` sources, SSE parsing, WebSocket frames, gRPC framing, stream
  statistics), `fault_tests.rs`; the shaped endpoint, the correlator's `RunEntry` (faults, churn turn,
  `done`), a server fault task on the harness (`watch_server_faults`), `ServerAssignment.faults` and
  `churn_slot`, and a test proxy that counts connections and HTTP/2 requests and forwards as HTTP/1.1.
- **Client faults** are drawn per request from a seed of the run id (`draws`), so every node draws the
  same way for the same request. Built: `connection_churn` (a pool-less client per target), `abandon`
  (the exchange is cancelled after `after`; `totals.abandoned`, neither answered nor failed), `slow_body`
  (the request body streamed in pieces every 100 ms: the client body became a `BoxBody`), `malformed_json`
  (the body cut in half), `wrong_content_type` (`text/plain`), `oversized_headers` (`X-Rustybin-Padding`),
  `retry_on_5xx` (`synchronised` waits for the next whole second of the run clock), `expired_tokens`
  (a JWT expired a minute ago, needs `identities.jwt`) and `http2` (every target has an HTTP/1.1-only
  and an HTTP/2-only client: ALPN on TLS, prior knowledge on plain targets; the fraction picks). Requests
  made to be refused expect any 4xx. Not built: half-open connections and resets mid-body on the client
  side (`abandon` cancels whole exchanges), revoked tokens (no revocation registry to churn), TLS
  handshake bursts beyond what `connection_churn` makes. Synchronised bursts are the patterns' `sync:
  cluster` (phase 4); WebSocket bursts are the `websocket` source under a `burst` pattern; SSE readers
  that never read are `sse.hold_unread`.
- **Server faults** act only on the run's marked requests at `/harness/{*path}` and on `/health`, never
  on other routes. `drop` sends the headers and the body's first byte, then an error ends the body (the
  connection is reset; through a gateway that forwards bodies the client sees the same); `stall` sends
  the headers then nothing for `for`; `flapping_health` and `churn` flip the node's `HealthState` from a
  task per run on the node (50 ms ticks) that stops when the run ends and leaves the node healthy. Churn
  is by turns without a leader tick: the leader gives each server node its index and the count
  (`churn_slot`), and node `index` is down during window `index` of every `count` windows of `every`;
  while down, marked requests get a 503 with `Connection: close`. A single node takes turn 0 of 1. Not
  built: `leave and rejoin` (a server node leaving the cluster and coming back); churn stops the node
  serving instead.
- **Presets** are named blocks resolved field by field (a field set in the scenario replaces the
  preset's): `calm`, `jittery`, `flaky-upstream`, `retries`, `synchronised`, `churn`, `all`. The live
  change `faults` replaces the block whole; server nodes take it on their next heartbeat.
- **Protocol sources** resolve into one request template per layer (no node resources needed), read by
  protocol in the engine: `llm` and `sse` stream event by event (SSE parsing in the engine, an item
  per token or event, the request timeout as the idle timeout between bytes, a stream never longer
  than ten timeouts plus a hold), `websocket` upgrades over the HTTP/1.1 client and speaks masked
  frames itself (no new dependency; a round trip is an item; pings answered; a close frame at the end),
  `grpc` sends a prost-encoded `EchoRequest` in a length-prefixed frame over HTTP/2 and reads
  `grpc-status` from the trailers (or the headers of a trailers-only answer), `mcp` sends a stateless
  2026-07-28 `tools/call` with its `_meta` and the `Mcp-Method` / `Mcp-Name` headers and reads the
  result's `isError`. Only unary gRPC and `tools/call` are built; the streaming gRPC methods and other
  MCP methods are not. The request timeout bounds HTTP, gRPC and MCP exchanges whole.
- **Attribution**: a gRPC answer never carries the served-by tag (its service is outside the server
  layer); a WebSocket upgrade through a Rustybin server's layer does. Without a tag these count as
  `unattributed`, a fourth class next to upstream, gateway and transport (never as gateway-made).
- **Stream metrics** per layer (`report.streams`): streams, items per stream and per second, the time to
  the first item, the gaps between items, the stream length (exact histograms, merged across nodes
  through the final stats), stalled and incomplete streams. A streamed answer's latency is the
  stream's length; the gateway overhead and the response leg are not measured on streamed answers
  (they would be the stream's length too). Checked against the mock LLM's pacing
  headers (`X-Rustybin-TTFT-Ms`, `X-Rustybin-Tokens-Per-Second`): a 200 ms TTFT and 50 tokens per
  second come out as a first-token p50 near 200 ms and a 20 ms gap.
- **Surfaces**: the schema (`$defs.faults`, the five source kinds, the `faults` change), so the MCP tool
  schemas and the console builder have them; the report's `streams`, `totals.faults`, `abandoned` and
  `unattributed` in JSON, text, the console and the MCP summary; built-ins `llm-streaming`,
  `flaky-upstream` and `jittery-clients`. No new routes.

## 16. Testing

- Unit tests next to each part: scenario validation, scheduler timing (on the injectable clock that
  `limits::Clock` already provides), signing, classification, histogram merge, allowlist and pinning,
  lease expiry, succession ordering and tie breaks, vote rules, term fencing.
- Election tests run the nodes in one process on the injectable clock. A test can then drop links between
  chosen pairs (partitions, a candidate that only lost its own link) and advance time deterministically,
  with no sleeps.
- A test proxy in `src/harness/test_proxy.rs` (`cfg(test)`, a few dozen lines of hyper). It stands in for
  "the gateway": it adds and removes headers, answers its own 429 and 503, delays, and drops requests on
  command. It runs several instances to stand in for a gateway fleet. It has small reference rate
  limiters (fixed window, sliding window, token bucket; shared or per instance counters) with known
  flaws to switch on, so every rate-limit test has something to find. It is vendor neutral and fast.
- Pattern tests check the preview curve against the math and the achieved rate against the preview, on
  the injectable clock.
- Full-app tests start real servers on ephemeral ports (the `tests/integration.rs` pattern). Rates in
  tests stay low (hundreds of rps for a second or two) to keep the suite fast; throughput numbers belong
  to phase 0 and the conformance run, not to `cargo test`.

## 17. Open questions

1. **Leader handover on purpose**: `POST .../leader/transfer` to move the leader before maintenance, and
   rebalancing when the leader becomes the busiest node, if runs need it. Section 9.1 covers failure only.
2. **OpenTelemetry export** (OTLP traces and metrics) from clients and servers, in addition to
   Prometheus and the report.
3. **HTTP/3** targets.
4. **Recording and replay**: replay captured inspector traffic (or a HAR file) as a traffic source.
5. **Scenario import** from other tools' formats, if users ask for it.
6. **Server-to-server chains**: servers that call further servers, for multi-hop meshes. That is
   outbound traffic from the server role, so it stays out until the safety model covers it.
